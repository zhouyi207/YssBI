## 一、当前项目的实际情况，与前面那份通用方案有几个重要区别

### 1. Graph 当前并不是通过 Polars LazyFrame 执行的

当前图相关的主要路径是：

```text
GraphDocument
    ↓
GraphSemanticSnapshot
    ↓
GraphCompiledPackage
    ↓
Application 组装执行包、绑定资源
    ↓
yss-execution
    ↓
KernelRegistry
    ↓
RuntimeValue / ResultStore
```

`yss-graph-compiler` 已经是中性的 Graph lowering 模块，不依赖 Project authority、Application 编排或 Execution 自己的包模型。它不应该因为引入 DataFusion 就被整体删除。

更关键的是，当前 `yss-execution/src/state.rs` 的 `KernelRegistry` 注册了 OLS、常量、标量数学、逻辑、比较、类型转换、View 和 Reroute 等 kernel，**并没有注册 DataFrame 数据源、筛选、投影、列选择等关系执行 kernel**。

但这些节点已经存在于目录中，例如：

```text
yssbi.dataframe.source.get
yssbi.dataframe.limit
yssbi.dataframe.rename
yssbi.dataframe.project
yssbi.dataframe.filter.rows
yssbi.dataframe.decompose
yssbi.dataframe.combine
yssbi.dataframe.series.select
```

因此，**节点定义、Schema 解析、配置编辑已经存在，不代表对应计算链路已经完整实现**。

这反而使现在成为比较合适的接入点：不必先补齐一套 Polars 执行，再立刻推倒重来。

### 2. DuckDB 已经承担了真正的数据库职责

当前并不是简单地“用 DuckDB 查询一下文件”。

`yss-database-runtime` 的现行设计是：

```text
database/project.duckdb
    ├── 用户数据表
    ├── physical schema
    └── display metadata
```

分页、按列读取、统计概览、导出、单元格编辑、行列增删、类型转换和撤销，都已经围绕这个存储实现。DataView 使用 DuckDB `rowid`；编辑通过 SQL 事务完成，运行时不维护可编辑的整表 DataFrame。

因此：

> **替换查询计算相对直接；替换 DuckDB 的编辑与持久化保证，才是迁移中工作量最大、风险最高的部分。**

### 3. SQLite 不是需要“从零新增”的基础设施

工作区已有：

```text
yss-project-registry-sqlite
yss-statistical-harness-sqlite
```

并且已经使用启用了 SQLite 的 `sqlx`。你需要新增的是**项目数据集目录和编辑版本的持久化职责**，而不是重新建设全部 SQLite 基础设施。

但也不要把这两个已有适配器直接变成通用数据集仓库。它们原来的职责与数据集存储不是一回事。

### 4. “Yss Stats” 在代码里已经存在，不需要再造一个引擎

现在的科学计算边界已经是：

```text
yss-sci-contract
       ↑
yss-sci-runtime
       ↓
yss-sci
       ↓
yss-linalg
```

数值算法核心已经脱离 Polars，Polars 主要还在部分表格准备和适配路径中。

例如现有 `OlsRequest` 本身就是：

```rust
pub struct OlsRequest {
    pub response: Vec<f64>,
    pub predictors: Vec<Vec<f64>>,
    pub options: OlsOptions,
}
```

所以第一阶段应当做的是：

```text
DataFusion
    ↓ Arrow batches
统计输入准备
    ↓ OlsRequest
现有 ScientificBackend::ols
```

而不是让 OLS、线性代数和所有统计契约都改成依赖 DataFusion。

## 二、适合你当前项目的目标架构

我建议把目标明确成下面这样：

```text
GraphDocument
    ↓
GraphSemanticSnapshot
    ↓
现有 Graph Compiler / compiled artifact
    ↓
执行准备：关系子图 lowering + 统计/标量调度
    │
    ├── DataFusion adapter
    │       ↓
    │   LogicalPlan + execution context
    │       ↓
    │   Arrow RecordBatch stream
    │
    └── 现有 ScientificBackend
            ↓
        yss-sci / yss-linalg


DatabaseRuntimeSession
    ↓
数据集快照、查询、编辑接口
    ↓
Dataset storage
    ├── SQLite：catalog、schema metadata、版本、稀疏编辑
    └── Parquet：不可变基础数据文件


Project / Graph 文档保存 / publication / Results
    └── 保留现有 authority 与生命周期
```

这里有三个边界需要坚持。

**第一，`GraphSemanticSnapshot` 继续是图语义的唯一对外权威。** DataFusion 的类型推导应成为关系节点解析的实现依据之一，最终仍由同一次 Resolve 形成完整 snapshot，不能另起一份“DataFusion Schema Store”让前端自行协调。你现在已经建立了这个统一边界，应当保留。

**第二，DataFusion 具体类型尽量收在适配器内。** 不要把 `SessionContext`、`LogicalPlan` 塞进持久化的 `GraphDocument` 或前端 DTO。DataFusion 的 `DataFrame` 实际还包装了执行所需的 `SessionState`，并不只是一个脱离上下文的计划树。([Docs.rs][1])

**第三，现有 Graph 编译包可以保留，但不要再复制一套关系优化器。** Graph 包拥有节点身份、输入输出地址、资源依赖和统计调用关系；DataFusion 拥有关系子图的表达式、优化和执行。这是不同职责，不是因为同时出现两种“Plan”就必须删除其中一个。

## 三、首先改执行层：这是迁移的第一条主线

### 1. 第一处关键改动：`RuntimeValue` 与资源绑定

当前 `RuntimeValue` 主要是：

```rust
Null
Bool
Integer
Unsigned
Decimal
String
List
Record
Resource(Box<str>)
```

DataFrame、DataSeries 等值会被转换成字符串资源句柄，**还没有表达“可组合的关系计划”的类型**。

生产执行资源绑定目前也会构造：

```rust
RuntimeValue::Resource(resource.as_str().into())
```

而不是绑定一个可以扫描的、版本固定的数据集。

建议在现有执行端口和资源准备边界中引入明确的概念，名称可以调整：

```text
RelationHandle
    = 一段关系计算 + 固定的数据快照 + 执行上下文租约

SeriesHandle
    = 某个关系上的列/表达式 + 行对齐信息
```

这里的核心不是多加两个枚举成员，而是让句柄明确回答：

| 问题          | 应由句柄及其所属运行时确定        |
| ----------- | -------------------- |
| 属于哪个项目会话？   | session / generation |
| 读取哪个版本的数据？  | dataset snapshot     |
| 代表什么计算？     | 已准备的关系计划             |
| 对应哪些列和类型？   | 已解析 Schema           |
| 两条数列能否逐行组合？ | 共同的行域与对齐规则           |
| 文件什么时候可以删除？ | 快照与结果持有的租约           |

重点修改位置是：

```text
yss-execution/src/value.rs
yss-execution/src/resource_preparation.rs
yss-execution/src/ports/
yss-application/src/execution/run_graph.rs
yss-application/src/execution/session_factory.rs
```

现有资源准备已经检查 session、版本、需求和授权；**应当扩展这个边界，不要绕过它直接从节点里访问数据库路径**。

### 2. 不要让每个关系节点执行一次查询

当前调度器逐节点解析输入、调用 kernel，并把每个输出放入 `RuntimeValue` 槽位和候选 Results。

因此，下面这种接入方式应当避免：

```text
Source.collect()
    ↓
Filter.collect()
    ↓
Project.collect()
    ↓
OLS
```

否则只是换了计算库，仍然没有跨节点优化。

建议让连续关系节点构造一段完整计划：

```text
Source
    ↓
Filter
    ↓
Project
    ↓
Select Y / Select X
    ↓
统计输入准备
```

直到统计输入准备时，才执行组合好的查询。

在实现上，可以由 DataFusion 适配器遍历现有编译包中的关系节点，将其 lowering 为原生 `LogicalPlan`；现有调度器继续处理标量、统计调用和跨边界依赖。不需要另造一个与 DataFusion 几乎相同的 `Filter/Join/Aggregate` 优化 IR。

**另外，后端能力检查应当进入 Compile。** 未实现的关系算子不能在新链路中表现为“编译成功，运行时才发现 KernelNotFound”。这是当前目录定义与执行实现之间需要一并收紧的契约。

### 3. 第一条完整链路就做这几个现有节点

我建议最先打通：

```text
yssbi.dataframe.source.get
          ↓
yssbi.dataframe.project
          ↓
yssbi.dataframe.filter.rows
          ↓
yssbi.dataframe.series.select
          ↓
yssbi.statistics.ols.fit / summary
```

已有节点目录和 OLS 契约足够支撑这个目标，不必第一轮同时实现 Join、全部时间序列节点、WLS、GLM、函数子图执行和插件统计。当前架构文档也明确说明，OLS 已接入的是物化数值序列，而数据库/序列句柄物化以及其他模型执行仍有未接通部分。

这里的验收不只是“算出了一个回归结果”，还应包括：

```text
Compile 不读取整表
投影、筛选进入同一关系计划
没有中间节点整表 collect
只准备统计需要的列
结果仍走现有 finalization / ResultStore
```

### 4. `SeriesHandle` 必须解决行对齐

这一点对统计软件尤其重要。

不要把：

```text
Y 单独查询、收集
X1 单独查询、收集
X2 单独查询、收集
```

然后简单按照数组下标拼成回归样本。

建议同一模型的数据输入尽量合成一次共同投影：

```text
同一个关系、同一个快照
    ↓
SELECT row_identity, y, x1, x2
    ↓
一次读取
    ↓
统一处理缺失值、类型和样本对齐
    ↓
OlsRequest
```

来自不同过滤、排序或 Join 结果的数列，不能仅凭长度相同就认定可以对应。`decompose`、`combine`、布尔 mask 筛选也需要遵循同样的行域规则。

第一版可以保守：**只允许有共同关系来源和对齐依据的数列直接组合；其他情况要求显式 Join/对齐操作。**

### 5. Results 不能把“懒执行”重新变成整表缓存

目前调度器会为执行到的输出建立候选结果；若把每个 DataFrame 输出都直接保存为全部 Arrow batches，长链路仍然会保留很多中间数据。

建议区分：

```text
标量/统计结果
    → 保存实际 payload

关系结果
    → 保存绑定本次运行快照的关系句柄

用户预览关系结果
    → 对这个句柄做有界分页查询
```

但这需要明确一个行为边界：关系句柄表示已解析的查询结果入口，并不证明所有行都已经成功计算。可能在扫描时发生的错误，应由分页/物化请求明确报告，不能把“计划已准备”冒充“全部数据已执行”。

无论采用哪种结果表现，旧结果都不能在打开时悄悄读取“数据集最新版本”。你现有的 ResultStore 失效、取消后不恢复旧 payload、拒绝迟到发布等规则应继续保留。

### 6. 同时处理异步、内存与取消

当前 `PreparedPlanExecutor` 是同步接口，科学计算端口也是同步接口；科学端口明确只保证入口处检查取消和 deadline，不保证计算开始后能够立即中断。

建议让关系执行边界支持异步批流，标量 kernel 可以继续同步，矩阵计算放在适当的计算线程执行。

DataFusion 的 `collect()` 会把输出批次全部收集进内存；`execute_stream()` 则提供批流。因此查询边界应优先消费批流，而不是默认 `collect()`。([Docs.rs][1])

但 **Arrow 流式输入不等于 OLS 自动变成流式算法**。现有 OLS 仍需要准备数值向量/矩阵，应当单独做统计输入内存预算。

另外，多个 DataFusion context 应共享受控的 `RuntimeEnv`，否则每个 context 各自建立资源限制，不能约束整个进程的查询总用量。([Docs.rs][2])

## 四、再改存储：不要把 Dataset 简化为一个 Parquet 路径

### 1. 保留现有 Database runtime owner，替换其内部存储实现

目前：

```rust
DatabaseState::DuckDb { ... }
```

以及：

```text
bind_duckdb_instance
remove_duckdb_table_if_needed
```

是明确的替换入口。

建议的项目数据布局可以是：

```text
project/
├── 现有项目 manifest
├── 现有 Graph / Chart 文档
│
└── database/
    ├── catalog.sqlite
    │
    └── datasets/
        └── <dataset_id>/
            └── <generation>/
                ├── part-000.parquet
                └── part-001.parquet
```

这里 SQLite 中保存的不是仅有一个 `parquet_path`，而是数据集的已提交描述：

```text
dataset identity
active snapshot
snapshot → 文件集合
精确 schema / 列身份 / 类别元数据
数据与 Schema 版本
稀疏编辑、插入和删除记录
提交恢复所需的 operation 状态
```

**项目打开应读取已提交 catalog，而不是扫描目录后把所有 Parquet 文件自动视为有效数据。** 失败导入和失败压缩都可能留下未提交文件。

DataFusion Catalog 只是该 catalog 的查询投影，不是第二份可独立修改的数据集定义。

### 2. 外部导入来源与内部存储身份继续分开

你已经有独立的 `DatabaseImportSource`：

```text
Csv / Sql / Parquet / Excel
```

但持久化 `DatabaseEngine` 中仍同时列着外部来源、DuckDb 和 InMemory 等变体。

这次适合把生产契约进一步收敛：

```text
DatabaseImportSource
    = 数据从哪里来

Dataset storage reference
    = 导入后由项目如何拥有它
```

不要把内部存储直接替换成现有的：

```rust
DatabaseEngine::Parquet { path, columns }
```

因为它表达的是文件来源，并没有表达快照、编辑、版本和文件生命周期。

### 3. 必须引入稳定行身份，并与显示顺序分开

当前页面结果包含 `row_ids: Vec<i64>`，编辑请求也支持 `row_id` 和期望 runtime revision。

这套接口值得复用，但新存储不能把下面这些当成长期身份：

```text
Parquet 文件内第几行
第几个 RecordBatch 的第几行
分页 offset
未明确排序时临时计算的行号
```

建议：

```text
RowId       = 数据行身份，不因编辑、压缩、重排改变
DisplayOrder = 表格展示位置，允许改变
```

你当前还有按指定 index 添加行的操作，因此只保存单调 RowId 并按它排序，未必能够表达全部现有编辑行为。

列也应有稳定身份。否则 Delta 以列名作为键，重命名列以后就必须同步改写大量历史记录。建议将 `ColumnId` 与用户可修改的显示名称分离。

### 4. 精确存储 Schema 与图逻辑类型必须分开

当前 `yss-database-schema/src/lib.rs` 中存在粗粒度映射：

```text
UInt64 / UInt32 / Int32 ... → Int64
Decimal / Float32 ...     → Float64
不同时间单位/时区信息       → Datetime
```

这可以用于某些图端口分类，**但不能作为无损重建存储的依据**。

建议保留两个不同层次的事实：

| 层次          | 用途                                          |
| ----------- | ------------------------------------------- |
| 精确存储 Schema | Arrow 类型、Decimal 精度和 scale、时间单位/时区、类别定义、列身份 |
| YssBI 语义类型  | 节点连接、可用操作、统计输入约束、编辑器投影                      |

二者通过一个明确映射连接，而不是通过几次字符串转换来回猜类型。

同时要区分“列允许 NULL”与“当前扫描的数据里有没有 NULL”。不要因为一批数据暂时没有缺失值，就把存储契约变成不可空。

### 5. Delta 合并与 pushdown 的顺序，是必须先解决的正确性问题

以前面的例子为例：

```text
Parquet 中 income = 8000
编辑记录把它改为 9000

查询条件：income > 8500
```

如果实现为：

```text
先在 Parquet 上应用 income > 8500
    ↓
再合并编辑记录
```

这一行会先被过滤掉，最终结果错误。

正确的逻辑是：

```text
Base snapshot
    +
该快照可见的 edits / inserts / deletes
    ↓
当前数据集视图
    ↓
用户的过滤、聚合、limit
```

因此首版自定义 `TableProvider` 应保守处理下推：

**对尚未证明安全的谓词，不下推到编辑覆盖之前；`limit` 同样不能提前截断。** DataFusion 的接口明确区分 `Exact`、`Inexact` 和 `Unsupported`，并对不精确过滤与 limit 下推有约束。([Docs.rs][3])

这里也不能以为“标成 Inexact、最后再过滤一次”就总能解决：已经被基础扫描错误丢掉的行，后置过滤无法找回来。

实现 Delta 还应区分：

```text
这个单元格没有编辑记录
```

和：

```text
这个单元格被明确设置为 NULL
```

不能简单用 `coalesce(edited_value, base_value)` 表达覆盖。

### 6. SQLite 只保存有界编辑，批量变换生成新快照

我不建议把所有批量变换都展开成 SQLite 中数百万条单元格编辑。

更适合的策略是：

| 操作                 | 建议实现               |
| ------------------ | ------------------ |
| 少量单元格修改            | 类型明确的稀疏 Delta      |
| 少量插入/删除            | 插入记录与 tombstone    |
| 列重命名               | Schema metadata 变更 |
| 大规模 cast、批量修改、结构重写 | 生成新的不可变数据快照        |
| Delta 增长过大         | 合并压缩并发布新快照         |

类别数据还要保留类别集合、顺序等语义，不能把某个 Arrow batch 中的字典编码数字当成跨批次、跨文件的全局类别身份。

### 7. 文件与 SQLite 之间需要明确的提交协议

建议将数据集提交过程定义为：

```text
准备新数据文件
    ↓
写入完成、关闭、执行必要同步
    ↓
放入不可变的最终文件位置
    ↓
重验 Project session / expected revision
    ↓
SQLite 事务发布新快照与提交交接记录
    ↓
安装当前运行时状态并发布 Project change
```

需要覆盖两个不同的失败窗口：

```text
catalog 提交前失败
    → 旧快照继续有效，新文件可以回收

catalog 提交后、运行时发布前失败
    → 恢复已提交状态与 publication
    → 不能假装数据没有提交
```

**Parquet 文件和 SQLite 行并不因为都在本地，就自动成为同一个原子事务。**

应复用你已有的 Project gate、prepared/committed mutation、操作身份、文件租约及恢复机制，而不是再建一个相互竞争的事务管理器。现有导入已经有 session 捕获、文件租约、最终校验和声明提交这些步骤；迁移应替换存储交接，不要删掉它们。

旧文件也不能在 compaction 后立即删除：正在运行的查询、当前关系结果以及可撤销操作可能仍然引用它们。

### 8. Save、Undo 和 Compaction 不要混成一个操作

当前 `save_database_changes` 对 DuckDB 主要是刷新 metadata、清空编辑历史，不会重建整表。

迁移后建议继续明确：

```text
Edit       = 提交一次数据变化
Undo/Redo  = 根据历史执行相反/正向变化
Save       = 既有用户层保存语义
Compaction = 存储整理
```

**清空 Undo 历史，不等于清空持久化 Delta；保存，也不应默认重写整份大表。**

## 五、按现有 crate 划分，具体怎么处理

下面是我建议的模块处理方式。新增名称是建议，不是声称仓库已经存在。

| 当前模块                                      | 建议                                                         |
| ----------------------------------------- | ---------------------------------------------------------- |
| `yss-graph-document`、`yss-graph-analysis` | 保留文档、类型、Schema、lineage 和诊断权威；让关系节点解析与后端能力一致                |
| `yss-graph-compiler`                      | 保留中性编译包；增加关系子图 lowering 的交接，不重做通用关系优化器                     |
| `yss-execution`                           | 增加关系/数列句柄、关系阶段调度、受控物化；保留 demand、run 和 ResultStore 生命周期     |
| **新增 `yss-datafusion`**                   | 集中拥有 DataFusion 计划构造、表达式映射、Provider 接入和查询执行                |
| `yss-database-runtime`                    | 保留 session、revision、query/edit 编排；将 DuckDB state 改为数据集快照存储 |
| `yss-database-contract`                   | 保留身份和导入来源；收敛内部存储引用                                         |
| `yss-database-schema`                     | 保留中性 Schema facts；把 DuckDB/Polars 转换移到适配层，补足精确存储信息         |
| `yss-tabular-polars`                      | 由 **`yss-tabular-arrow`** 替换其宿主职责；保留分页 DTO 与表格值之间的严格转换     |
| `yss-tabular-io`                          | CSV/Parquet 改为 Arrow 批处理；Excel 解码职责继续保留                    |
| `yss-sql-source`                          | 保留 SQLx 和外部数据库解码；输出从 Polars DataFrame 改为 Arrow batches     |
| `yss-dataset-profile`                     | 保留现有结果契约；查询型统计转到 DataFusion，避免因为迁移改变统计口径                   |
| `yss-sci-runtime`                         | 改造仍依赖 Polars 的输入准备；不改写已有数值算法核心                             |
| `yss-duckdb`                              | 所有实际消费者完成迁移后删除，而不是简单改名为 `yss-datafusion`                   |

上述存储、编辑和转换职责在数据库 runtime 文档中已经分得比较清楚；沿现有 owner 替换实现，比重新增加一组“万能 backend / engine manager”更合适。

有两点容易漏掉。

**外部 SQL 与 Excel 导入仍然需要自己的适配器。** 当前 `yss-tabular-io` 使用 `calamine`；`yss-sql-source` 使用 SQLx。当前 SQL 导入还会先调用 `read_table_to_dataframe`，所以这条路径应改为有界批处理，不能只把最后的 DuckDB Appender 换成 Parquet Writer。

**原始分阶段范围：宿主移除 Polars，不等于整个工作区立即没有 Polars。** 当时三个 Julia/Bayes 插件 crate 仍有直接依赖，建议独立迁移。
后续用户已明确要求继续替换插件；该独立阶段现采用 DataFusion 查询和 Arrow 交换文件，当前职责见 [Julia 插件](../../plugins/julia/README.md)。

## 六、建议拆成五个工作包，而不是一次巨型替换

### 工作包 A：统一 Arrow 与精确 Schema 边界

先处理 `yss-database-schema`、`yss-tabular-polars` 的职责拆分和新的 Arrow 适配。

明确数据类型、NULL、类别、行身份和版本契约；将 DataFusion、Arrow、Parquet 的依赖版本统一锁定，避免新旧 Arrow Rust 类型在公共接口里混用。

**完成条件：** Arrow 批次能无损通过宿主数据边界；分页 DTO 继续工作；统计核心无需依赖 DataFusion。

### 工作包 B：完成关系执行到 OLS 的最小闭环

新增 DataFusion 适配器，改造执行句柄和资源准备，将已有 source/project/filter/series-select 节点连到现有 OLS。

这一阶段先使用固定的 Parquet 测试数据集验证完整后端链路，**不必为了验证计算层，提前切换真实项目的可编辑存储**。

**完成条件：** 组合计划正确、统计样本对齐正确、中间不整表物化、缺失值策略没有被悄悄改变。

### 工作包 C：实现数据集 catalog、快照和只读查询

实现 SQLite manifest、不可变 Parquet 文件、项目激活、分页、按列读取、profile 与 export。

把新存储接入现有 `DatabaseRuntimeSession` 与 Project publication。

**完成条件：** 项目重开后能够恢复同一份已提交数据；只读取 manifest 指向的文件；查询绑定明确快照。

### 工作包 D：实现编辑、Undo/Redo、恢复，然后切换项目格式

完成稀疏编辑、行列操作、类型转换、撤销边界、compaction 和失败恢复，再正式替换 DuckDB 项目存储。

当前项目格式版本是 **4**，而且仓库明确只支持当前格式，不自动兼容旧格式。这里应显式提升格式版本，不应偷偷保留 DuckDB 读取回退。需要保留的数据应先备份或导出，旧项目原件不应被升级过程破坏。

**完成条件：** 编辑能力没有退化；新格式项目完整可用；生产路径不再需要 DuckDB。

### 工作包 E：清理宿主 Polars 与旧存储路径

迁移 SQL 导入、Excel/文件 I/O、profile、SCI 输入准备等剩余消费者，然后删除不再被宿主使用的旧转换实现。

同步更新架构文档、模块图和相关依赖门禁。

**完成条件：** 宿主构建图达到目标依赖结构，没有废弃旧路径；插件内部是否继续使用 Polars 单独记录。

这五个工作包可以顺序提交在迁移分支上。**逐步实施不意味着最终保留两套执行权威，也不要求每个中间提交都向用户暴露新旧引擎切换选项。**

## 七、验证应该围绕迁移风险，而不是只看 benchmark

我建议优先覆盖这些不同的失败模式，而不是为每个节点机械复制整套测试：

| 验证主题        | 必须证明的行为                                   |
| ----------- | ----------------------------------------- |
| 懒执行与优化      | Compile 不读取整表，连续关系操作没有中间全量物化              |
| 统计样本对齐      | 多批次、过滤和重排后，Y/X 与预测值、残差仍对应同一组样本            |
| Delta 查询正确性 | 修改后的行能够进入或退出过滤结果；显式 NULL、删除和 limit 正确     |
| 身份与编辑       | 翻页、插行、压缩后 RowId 不变，列重命名不破坏编辑记录            |
| 精确类型        | UInt64、Decimal、时间信息、类别数据不因粗粒度 Schema 映射丢失 |
| 失败恢复        | 文件写入失败、catalog 提交前后故障、项目切换与迟到结果均有正确处理     |

执行层改动要验证调用方，不应只测试新建的 `yss-datafusion`。存储切换还应沿用现有数据库集成测试的行为要求。

仓库已有正确的聚焦入口，例如：

```sh
pnpm test:rs:package -p yss-execution --lib
pnpm test:rs:package -p yss-application --test numeric_execution
pnpm test:rs:package -p yssbi --test database_test
```

这些应按工作包选择，而不是每个小修改都运行。`test:rs` 本身是 workspace 入口，不能通过随手追加 `-p` 来代替 `:package` 聚焦命令。

性能验证则至少区分：

```text
冷启动与首次扫描
重复查询
窄列投影
高选择性过滤
少量编辑后的查询
大规模 cast / compaction
OLS 输入准备与矩阵计算
```

不要只测一个 groupby 就断言整体迁移更快。对你的应用而言，预览延迟、峰值内存、编辑响应和统计输入准备同样重要。

还有一点与你前面关心的缓存相关：DataFusion 当前 `cache()` 默认是缓存为内存表，并不是自动提供 YssBI 所需的持久化、按版本失效的节点缓存。**编译计划缓存、查询数据缓存和当前 ResultStore 必须分开设计。**([Docs.rs][1])

## 最后，我建议你现在具体从哪里开始

**第一批改动应集中在：**

```text
yss-database-schema
yss-tabular-* 的 Arrow 适配边界
yss-execution 的 value / resource_preparation / ports
新的 yss-datafusion
```

然后马上做出：

```text
固定数据集
    ↓
Source → Project → Filter → Series
    ↓
现有 OLS
    ↓
现有 ResultStore
```

这条验证链。

**第一批不要做的事情是：把 `project.duckdb` 直接改成 Parquet 路径、删除 Graph Compiler、重写统计核心、迁移全部 Graph 文档到 SQLite、同时清理 Julia 插件。**

另外，前面那份建议中“只依赖公开接口就比较稳定”需要稍微修正：公开接口仍可能在 DataFusion 大版本间变化，官方升级指南就记录过执行组件替换。因此应当固定版本、集中适配、随升级验证，而不是把公开 API 当成长期不变的 ABI。([Apache DataFusion][4])

**整体判断：你现在的 Graph authority、编译产物、session/revision 和统计契约已经提供了不错的迁移基础。真正需要新增的是可组合关系执行和版本化数据集存储；不需要推倒整个 YssBI。**

本次是基于当前提交的源码与契约审查，没有修改仓库，也没有运行编译、测试或性能基准；上述完成条件是迁移验收要求，不是已经验证通过的结果。
