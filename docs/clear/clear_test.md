请分析 `zhouyi207/yssbi` 仓库中的测试，并清理低价值、过度针对实现细节、仅用于修复历史小 bug 的测试。

目标不是单纯减少测试数量，而是提高测试信噪比、降低维护成本，并保留真正能够保护系统行为和架构契约的测试。

重点寻找并评估以下类型的测试：

1. **只验证字段“不存在”的测试**

   * 例如创建 JSON / payload / snapshot 后，仅断言：

     * `foo` 字段不存在
     * `without_xxx`
     * `does_not_include_xxx`
     * `removed_field_is_absent`
     * `json.get("xxx").is_none()`
     * `expect(obj.xxx).toBeUndefined()`
   * 如果这种测试只是为了防止某个已经删除的字段重新出现，而且没有对应的外部协议、兼容性、安全性或业务契约要求，优先删除。

2. **只针对历史小 bug 的单点回归测试**

   * 测试内容非常窄，只是在某次 bug 修复后验证一个局部实现细节。
   * 如果该行为已经被更高层的功能测试、契约测试、集成测试覆盖，则删除这个重复的小测试。
   * 不要因为测试注释中写有 “regression” 就自动保留。

3. **实现细节测试**

   * 测试私有字段、中间 JSON 形状、临时转换结果、内部函数调用顺序、内部缓存字段、具体 helper 输出等。
   * 如果重构内部实现但最终用户可观察行为不变时，该测试仍然会失败，则把它视为实现细节测试候选。

4. **重复测试**

   * 多个测试实际保护的是同一个行为，只是输入或断言有轻微区别。
   * 优先保留覆盖范围更广、更接近公开接口、更容易理解的一个测试。

5. **“构造对象 → serialize → 检查 JSON 某个字段”类测试**

   * 如果只是确认 serde / TypeScript 默认行为，且没有验证稳定的 IPC、持久化格式、插件协议、项目文件格式或公开 API 契约，则优先删除。
   * 不要测试语言、serde、JSON.stringify 等基础库本身已经保证的行为。

6. **已经失去意义的兼容性测试**

   * 检查旧字段、旧 alias、deprecated 字段、旧 migration 行为，但当前项目已经明确不再支持该版本。
   * 如果没有维护中的 backward compatibility contract，可以连同相关兼容逻辑一起删除。

7. **测试辅助逻辑比被测逻辑还复杂的测试**

   * 大量 mock、fixture、手工 JSON 拼装，只为了验证一个很小的布尔条件或字段。
   * 如果维护成本明显高于其风险保护价值，优先删除或合并。

---

### 必须保留的测试

不要为了减少数量删除以下测试：

* 公开 API / IPC contract
* 项目文件持久化格式
* 插件 protocol / SDK compatibility
* Graph / Draft / Resolver / Execution 的核心语义
* 数据导入、查询、统计计算正确性
* DataFusion / Arrow / Parquet 数据边界
* undo / redo 等用户可观察行为
* 权限、安全、路径处理、数据丢失风险
* migration 中仍然承诺支持的历史版本
* 曾经导致数据损坏、崩溃、错误计算、死锁或严重状态不一致的回归测试
* 很难通过其他测试覆盖的重要边界条件

---

### 判断标准

对于每个准备删除的测试，回答：

1. 它保护的是什么用户可观察行为或稳定契约？
2. 如果删除它，是否还有其他测试覆盖同一个风险？
3. 它是在测试 YssBI，还是在测试 serde / JSON / React / Rust / 标准库自身？
4. 仅仅修改内部实现、但最终行为完全不变时，它是否会失败？
5. 这个 bug 如果再次出现，严重程度是什么？
6. 这个测试的维护成本是否高于它实际提供的保护价值？

如果答案表现为：

* 没有明确外部契约
* 已经存在更高层覆盖
* 只验证内部表示
* bug 风险很低
* 测试维护成本较高

则可以删除。

---

### 执行方式

先扫描整个仓库测试，但不要直接批量删除。

将候选测试分成：

* `DELETE`：明显低价值，可以直接删除
* `MERGE`：和其他测试重复，应该合并
* `KEEP`：虽然测试很小，但保护重要契约
* `REVIEW`：是否删除存在风险，需要进一步判断

对于 `DELETE` 和 `MERGE`：

* 给出文件路径
* 测试名称
* 当前测试保护的行为
* 删除/合并理由
* 是否已有替代覆盖

然后执行清理。

同时检查：

* 被测试专门支撑的 fixture
* helper
* mock
* test-only type
* obsolete compatibility code

如果这些内容在测试删除后已经没有引用，也一起删除，避免留下死代码。

---

### 特别原则

不要以代码覆盖率为目标。

不要为了 coverage 保留“字段存在/不存在”“getter 返回值”“serde 输出形状”这类价值很低的测试。

更偏向：

`少量高价值行为测试 > 大量实现细节测试`

最终目标是让测试集中在：

`behavior + contract + correctness + regression of serious bugs`

而不是：

`implementation details + historical trivia + defensive assertions`

完成后，只运行与修改区域相关的最小测试集合，不要默认运行整个 workspace 的全部测试。
