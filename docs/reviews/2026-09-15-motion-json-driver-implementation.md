## OLS 报告试点

- `OlsReportSpec` 是独立的展示契约，不是 GraphDocumentPatch 或读投影 delta。
- 原报告的十类章节支持顺序和显示配置，以及当前结果绑定的 JSON 导入／导出。
- 字段、版本、ID、章节类型与数量严格校验，禁止递归布局与任意 props/actions。
- 数值、分页与检验继续读取真实 Results；完整报告引用必须匹配已读取的 descriptor。
- 配置一次验证后安装，非法输入保留上次有效报告。布局只保留于当前挂载视图，不持久化会话引用。
- 真实面板／窗口继续拥有结果租约；隐藏章节不会代替面板关闭，也不会更改后端结果绑定。

具体契约与边界见[Graph 与 Execution](../architecture/GRAPH_AND_EXECUTION.md#ols-语义报告布局)。

## 同一 OLS 样本的两种实现

[样本](probes/ols-layout-result.json) 由真实 Application → Graph Execute → ResultStore → DTO 链路生成，
含 1,000 个观测、模型概览、系数页和 200 个系统抽样残差点。文件中的执行会话已结束，不能拿该引用请求生产数据。
两种实现均复用生产 `ModelSummaryGrid`、`CoefficientsBlock`、`ReportSection` 与 `ScatterChart`。

- [类型化解释器](probes/report-layout/typed.jsx) 使用章节数组直接渲染。
- [受限 catalog](probes/report-layout/catalog.jsx) 将同一语义 Spec 转成 json-render 的 flat element map，
  只注册三种样本章节及根容器；props 为空且严格，action handlers 为空。
- 两者共用语义边界校验。json-render 的组件 props schema 不能代替结果授权、章节数量和本应用的平面结构限制。
- 数值、任意命令、错会话／错结果、未知章节、重复 ID、嵌套内容与超量章节均进入拒绝路径。
- 比较后的规范化 HTML 摘要一致，样式类来自同一组件。真实布局和主题视觉仍须桌面人工确认。

测量程序和全部 p50/p95/p99 数据见[脚本](probes/report-layout/compare.mjs)与[输出](probes/report-layout-comparison.json)。

| 指标                               | 类型化解释器 | 受限 catalog |
| ---------------------------------- | ------------ | ------------ |
| 适配代码（不含双方共用校验与章节） | 17 行        | 60 行        |
| 实验 bundle gzip                   | 368,252 字节 | 467,079 字节 |
| 校验 p95                           | 0.0020 ms    | 0.0061 ms    |
| DOM 模拟更新 p95                   | 0.5229 ms    | 0.5841 ms    |

bundle 指标包含双方共享的章节依赖并排除共享 React；应比较两者差值，不把实验 bundle 总量当作应用安装包增量。
DOM 更新使用 happy-dom，没有真实布局、绘制、Tauri IPC 或桌面帧率；不能据此宣称端到端性能达标。

在本次受限平面报告上，catalog 增加适配和运行时依赖，未展示足以抵消成本的维护收益，因此生产保留类型化解释器。
流式生成、跨结果报告和持久化模板若成为实际需求，再据测量重新评估；本次没有加入生产 json-render、Zod 或 Immer 依赖。
库的 catalog、registry 和 renderer API 参考[官方 catalog 文档](https://json-render.dev/docs/catalog)、
[官方 renderer 文档](https://json-render.dev/docs/renderers)；具体实验版本与输入由测量输出记录。

### 复现

从仓库根运行 Rust 样本生成：

```powershell
pnpm test:rs:package -p yss-application --lib export_report_layout_probe '--' --ignored --nocapture
```

在**仓库之外**建立一次性实验目录，写入独立 `package.json`，安装
`@json-render/core@0.20.0`、`@json-render/react@0.20.0`、`zod@4.3.6`、`react@19.2.8`，禁用 install scripts。
再从仓库根传入这个目录的 `node_modules`：

```powershell
pnpm bench:report-layout C:/path/to/isolated-probe/node_modules
```

### 提交恢复的具体约束

- 每个已接受的编辑、undo/redo 或 Save 推进 revision，即使正文没有变化。dirty 只比较当前内容与保存指纹。
- Project 最近请求回执限制为 128 条／2 MiB；单次创建身份映射最多 64 KiB，并在提交前检查。普通操作不保存完整图快照作为回执。
- GUI 按原 operation ID、请求版本、项目和图查询回执；已确认后读取最新投影。旧保存回执保留原保存版本，后续编辑仍为 dirty。
- Harness 用持久幂等键确定 capability invocation identity，再映射为 Project operation ID。丢失回执、迟到取消、账本收尾失败和通知关闭不把已提交的编辑改判失败。
- 同一 key 改写请求被拒绝；恢复只读取已有提交，不再次创建节点或端口。回执过期、编辑会话结束或进程崩溃时仍可能是未知结果，不推断回滚。
- 两端投影基线均限制为 32 条／32 MiB，单条超过 16 MiB 时不缓存；前端复用 Rust 的 `snapshotBytes` 计量。GUI 队列最多 64 个同图在途／待执行任务，独立图可继续前进。

### 行为回归证据

- Project 的 `graph_editing::tests` 检查内存编辑、undo/redo、显式保存、文件替换故障回滚、无失败回执、迟到提交、关闭重开、重命名，以及回执条目／字节淘汰后旧请求不能重写。
- Application 的 `automation::graph::tests` 复用真实 Project／Application，检查 GUI/Harness 的创建重试、保存后继续编辑、原创建身份恢复、批次失败和同一基线的竞争提交。
- Harness Core 的 `tools::tests` 注入账本首次 finish 失败、提交后取消与完成通知关闭，确认工具返回真实成功、原 Running 记录可由只读查询修复，写入只发生一次。
- 前端 Service／Application 协调检查覆盖坏 delta、丢失保存回执、未知回执、明确业务拒绝、投影缓存字节淘汰、队列过载与独立图前进。这些是传输和用例检查，不包含 UI 渲染单元测试。
