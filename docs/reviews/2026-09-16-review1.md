## 一、编辑与资源一致性问题

### 1. P1：连续修改节点的不同参数，后一次操作会覆盖前一次修改

**位置：**

```text
src/features/application/editor/setNodeParameters.ts
src/features/application/graphEditing/graphEditCoordinator.ts
src-tauri/crates/yss-graph-editor/src/mutation.rs
```

`setNodeParameters()` 现在仍然是**先读取当前文档、合并完整参数，再把操作放进队列**：

```ts
const document = useGraphEditingStore.getState().sessions[input.graphPath]?.document;
const merged = { ...document?.nodes[input.nodeId]?.parameters, ...input.parameters };
```

它传入的是已经构造好的 `setParameters` 对象；而 Rust 的处理是完整替换：

```rust
after.parameters = parameters;
```

所以，**任务虽然按顺序执行，第二个任务携带的完整参数却可能来自旧文档。**

独立控制流复核已经重现：

```text
初始：{ from: old_from, to: old_to }

操作 A：修改 from → new_from
操作 B：修改 to   → new_to
两者在 A 完成前先后入队

A 完成：{ from: new_from, to: old_to }
B 完成：{ from: old_from, to: new_to }  ← A 被改回去了
```

这里尤其需要注意：**后端 revision 校验不能解决这个问题。** 协调器在执行 B 时会读取最新版本，但 B 的参数内容已经提前构造好了。因此版本可以合法，内容仍然过期。

**修复建议：**复用现有的 `mutation(document)` 回调，把参数合并放到任务真正执行时进行。这个能力已经存在，不需要新增协调器或另一套版本机制。我用延迟合并方式对照，两个修改都能保留。

### 2. P1：关闭标签页不等待图编辑完成，可能卸载尚未保存的后端当前文档

**位置：**

```text
src/features/application/editor/workbenchPanelClose.ts
src/features/application/editor/graphDocumentRetention.ts
src/features/application/editor/graphDocumentUnload.ts
src-tauri/crates/yss-project/src/project_state/graph_lifecycle.rs
```

现在关闭流程使用的是**前端当前看到的 dirty 状态**。`shouldRetainGraphDocument()` 只检查是否聚焦、是否仍有打开的标签页、是否 dirty，没有检查该图的在途编辑或排队任务。关闭流程本身有一个队列，但不是 Graph 编辑使用的队列。

接着，`unloadGraphDocument()` 先清除前端投影和编辑会话，再发送卸载命令。Rust 的 `unload_graph_resource_for_lifecycle()` 则直接执行：

```rust
data.graphs.remove(graph_path);
self.graph_editing.lock().unwrap().remove(graph_path);
```

这里没有后端 dirty 检查，也没有区分“释放缓存”和“明确丢弃未保存文档”。IPC 和 Application 卸载入口同样没有等待图编辑队列。

存在这样的竞态：

```text
图原本已保存，前端 dirty=false
→ 发起编辑
→ Rust 已提交新文档，但响应尚未安装到前端
→ 用户关闭最后一个标签页
→ 前端仍按 dirty=false 处理，不提示保存
→ 卸载命令删除后端当前文档和历史
→ 磁盘仍是编辑前的内容
```

**这是源码能够支持的竞态路径，不是本轮已经在桌面上观察到的数据丢失。**

**修复建议：**关闭决策应先等待此前已接受的编辑完成，再读取权威保存状态。Rust 卸载边界也要保护未保存文档；用户确实选择“丢弃”时，应走带有明确意图和被确认编辑版本的路径，不能让普通缓存释放隐含执行丢弃。

### 3. P1：重命名函数只更新已加载的调用图，未加载的文件仍引用旧路径

**位置：**

```text
src-tauri/crates/yss-project/src/project_state/graph_lifecycle.rs
src-tauri/crates/yss-project/src/project_writers.rs
src-tauri/crates/yss-application/src/graph/resources.rs
```

`rename_graph_resource()` 查找引用时遍历的是：

```rust
for (path, resource) in &current_data.graphs {
    ...
}
```

而 `capture_writer_snapshot()` 只是复制内存中的 `ProjectData`，没有加载所有持久化图。Application 的重命名入口也没有先扫描未加载的调用图。

后面的文件事务，只写入重命名目标及上述遍历收集到的 `referenced` 图。也就是说，**磁盘上存在、但已经卸载或尚未打开的调用图，不会进入引用更新事务。**

触发场景：

```text
A.yssbi-event 调用 F.yssbi-function，并已保存
→ A 未加载
→ 把 F 重命名为 G
→ F 文件被移走
→ A 文件仍保存 target=F
→ 下次加载 A 时，引用指向已经不存在的函数
```

**修复建议：**基于项目文件索引或权威引用索引枚举受影响图，按需读取未加载文件，将引用更新纳入同一个文件事务。无需把所有图都打开成编辑器，但重命名结果不能取决于“调用图之前有没有打开过”。

### 4. P1：重命名没有更新动态端口的函数来源，已有连接会变成孤立端口

**位置：**

```text
src-tauri/crates/yss-project/src/project_state/graph_lifecycle.rs
src-tauri/crates/yss-graph-analysis/src/derived_ports.rs
src-tauri/crates/yss-graph-analysis/src/lib.rs
```

当前 `remap_document_references()` 只修改 `node.parameters` 内的字符串，没有修改动态端口绑定中的：

```rust
DynamicMemberLocator::FunctionParameter {
    function,
    parameter,
}
```

但函数派生端口的来源身份包含函数路径，解析阶段也是按照这个完整来源身份匹配已有绑定。

于是重命名后可能形成：

```text
调用节点 target：G.yssbi-function
已有端口 origin.function：F.yssbi-function
```

解析器找不到旧来源对应的新成员；被连接引用的旧端口会保留为 orphan，并产生 `PortOrphan`，同时为新来源生成新端口。**更新了节点目标，不等于保住了现有连接。**

历史重映射同样主要处理节点参数，没有完整处理动态绑定相关的补丁内容。

**修复建议：**重命名时同步更新当前文档、已保存文档和可逆历史中的类型化函数引用，并保留已有端口实例身份。复制图路径中已经存在 `duplicate_binding()` / `duplicate_locator()` 的类型化处理，可提取其中的引用重映射能力复用；不要照搬复制操作中重新分配身份的部分。

### 5. P2：重命名和复制会把普通文本误当成资源引用

**位置：**

```text
src-tauri/crates/yss-project/src/project_state/graph_lifecycle.rs
src-tauri/crates/yss-project/src/project_state/graph_editing.rs
```

这是与上一项相反的问题：**该改的结构化引用没有改，不该改的普通文本却可能被改。**

目前 `document_references()` 和 `remap_document_references()` 不看节点类型、参数键或参数语义，只要某个参数字符串等于旧图路径，就认为它是引用并替换。复制图以及历史重映射中也有相近逻辑。

一个具体例子是 DataFrame Rename 节点。它的 `from`、`to` 是普通文本参数，不是资源引用。假设用户设置：

```text
to = "functions/F.yssbi-function"
```

这只是希望得到这个名字的列；但重命名函数 F 时，该参数也会被替换，改变数据处理逻辑。

**修复建议：**建立一处类型感知的引用遍历与重写实现，供重命名、复制和历史处理共用。必须区分资源参数、动态端口来源与普通文本，不能继续以字符串相等作为资源引用判据。

## 二、统计推断与配置契约问题

### 6. P1：OLS 的稳健 Wald 检验分解失败，被转换成 `F=0、p=1`

**位置：**

```text
src-tauri/crates/yss-sci/src/regression/linear_model/ols/inference.rs
```

当前代码仍然有：

```rust
match v_matrix.as_ref().checked_cholesky() {
    Ok(llt) => {
        // 计算 Wald
    }
    Err(_) => 0.0,
}
```

随后将这个零值作为合法 Wald 统计量计算 F 和 p 值。因此，协方差矩阵无法分解时，最终会得到 **`F=0、p=1`**。

**“无法计算整体检验”不等于“整体效应为零、完全不显著”。** 这与上一轮判秩失败回退为零的问题类似，但发生在另一个仍然保留的错误分支。

我独立复核了这个分支：对奇异协方差，按当前回退规则确实生成 `F=0、p=1`。这只是错误分支复核，不代表运行了本仓库的 OLS 拟合器。

**修复建议：**整体检验返回明确的“不可计算”状态或类型化错误，不能用合法数值占位。若要支持降秩限制检验，需要明确可检验限制和自由度，而不是无条件回退为零。

### 7. P1：WLS 选择稳健协方差后，整体 F 检验仍使用经典公式

**位置：**

```text
src-tauri/crates/yss-sci/src/regression/linear_model/wls.rs
src-tauri/crates/yss-sci/src/regression/covariance.rs
```

平方和的修复已经存在，但当前 WLS 仍然先计算：

```rust
let f = ms_model / ms_residual;
```

之后才调用 `compute_cov_beta()` 根据 `covariance_type` 计算 HC1 等协方差。新的协方差用于标准误、t 值和置信区间，却没有用于整体 F 检验。

如果整体检验应与所选稳健协方差一致，就应使用相应的 Wald 形式。statsmodels 也明确区分：非稳健协方差使用均方比，其他情况使用排除截距的 Wald 型整体检验。([统计模型][1])

独立按源码公式重算，并与 statsmodels HC1 对照：

```text
x = [0, 1, 2, 3, 4]，包含截距
y = [1, 2, 1, 4, 3]
w = [1, 2, 4, 8, 16]
```

| 指标 | 当前 WLS 使用的经典公式 | 基于 HC1 协方差的整体检验 |
| -- | -------------: | --------------: |
| F  |       1.449548 |        3.750197 |
| p  |       0.314932 |        0.148213 |

这个模型只有一个斜率，对应 Wald F 应等于该斜率的稳健 t²；复核得到的 HC1 t² 是 `3.750197`，而不是当前整体 F 的 `1.449548`。

**影响范围要说清楚：**该问题针对配置了稳健 `WLSConfig.cov_type` 的底层调用。当前统一 `fit_regression()` 的 WLS 分支写死为 `nonrobust`，所以这不是本轮已复现的 GUI 默认 WLS 故障。

**修复建议：**先修第 6 项，再收口 OLS/WLS 的协方差感知推断逻辑，避免继续维护行为不同的两套整体检验。

### 8. P2：未知协方差名称会静默降级成 nonrobust，但报告仍保留原名称

**位置：**

```text
src-tauri/crates/yss-sci/src/regression/covariance.rs
src-tauri/crates/yss-sci/src/regression/linear_model/wls.rs
```

`compute_cov_beta()` 的默认分支是：

```rust
_ => cov_nonrobust(xtx_inv, u, df_residual),
```

而 WLS 会把输入的 `cov_type` 原样保留到结果的 `covariance_type`。

例如直接配置一个当前未实现的名称：

```text
WLSConfig.cov_type = "HC4"
```

可能得到：

```text
报告名称：HC4
实际计算：nonrobust
```

这比明确报错更危险，因为结果看起来支持了一种实际上没有执行的方法。

**修复建议：**未知值明确拒绝；默认值只处理“没有提供配置”，不能处理“提供了无效配置”。优先复用已有的类型化协方差配置，而不是让各模型继续维护自由字符串和 fallback。

同样，这里确认的是底层 API 行为，不代表前端当前允许输入任意协方差名称。

### 9. P2：GLS 对 Σ 的含义与推断分布不一致

**位置：**

```text
src-tauri/crates/yss-sci/src/regression/linear_model/gls.rs
src-tauri/crates/yss-sci/src/regression/fit.rs
```

当前 GLS 同时采用：

```text
协方差名称：GLS (known Sigma)
参数协方差：(X'Σ⁻¹X)⁻¹，不乘估计的残差尺度
p 值与置信区间：Student-t(df_residual)
```

这些选择在源码中是固定的，没有显式区分“完整协方差已知”与“只知道协方差结构”。

这两种模型需要不同处理：

**Σ 是完整已知协方差时，**在高斯 GLS 假设下，现有未缩放的参数协方差是合理的，但相应标准化系数应按 Normal 推断。

**只知道相对结构、还要估计公共尺度时，**可以使用相应的 t 推断，但参数协方差必须包含估计尺度。当前实现把前一种标准误和后一种推断分布组合在了一起。固定尺度与推断分布的选择也在 statsmodels 的结果配置中明确区分。([统计模型][2])

用前述 `x、y`、令 `Σ=I` 独立计算斜率检验：

```text
当前公式：已知 Σ 标准误 + Student-t → p ≈ 0.154031
高斯已知 Σ：相同标准误 + Normal    → p ≈ 0.057780
```

此外，统一 `fit_regression()` 的 GLS 分支没有接收 Σ，而是直接构造单位矩阵。这个入口需要一并明确：究竟提供“已知单位误差协方差”的模型，还是通常需要估计尺度的回归。

**修复建议：**先统一 Σ 的统计含义，再统一参数协方差、检验分布和报告标签；不能仅补一个尺度乘法或替换一个分布就宣告完成。

## 三、建议处理顺序与验证方式

| 批次      | 问题      | 重点                        |
| ------- | ------- | ------------------------- |
| **第一批** | 1、2     | 保证已接受的编辑不会被覆盖或因关闭标签页而释放   |
| **第二批** | 3、4、5   | 将重命名收敛为完整、类型感知的引用事务       |
| **第三批** | 6、7、8、9 | 统一统计推断契约，禁止失败或未知配置伪装成有效结果 |

编辑侧最值得人工验收的是：**连续修改两个参数后立即关闭；调用图未打开时重命名函数；带已有连线和字面量输入的函数重命名。** 这些场景对应不同失败机制，不能用“保存成功”“能重新打开项目”替代验收。

**结论：下一轮应先修编辑生命周期和重命名事务，而不是继续增加 revision 或兼容层。** 这里的问题主要不是消息丢失，而是**入队前读取了过期内容、卸载越过了编辑边界、引用重写不完整，以及数值失败被转换成了正常结果**。
