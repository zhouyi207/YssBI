**有，而且其中几项不只是“代码不够整洁”，而是会跳过已经提交的编辑，或者给出错误的统计结果。** 比较严重的发现集中在保存队列、数值比较、回归统计量、错误处理，以及前端快照的安装规则。

本轮检查固定在 `main` 的 **`164fcaec8adcd0b8bb3e708456962176f7a1b08a`**，不是根据以前的架构讨论推断当前实现。重点追踪了 Graph 编辑与保存、项目快照发布、节点目录与 Kernel、统计计算、Settings、Harness 持久化等调用链。对保存队列、设置覆盖和部分数值公式做了独立最小复现；**没有运行整个仓库的构建或 Tauri 桌面验收**。

下面按问题分组列出。**P1** 表示优先处理的状态或结果正确性问题；**P2** 表示契约问题、条件性风险或功能缺口；**P3** 表示清理与维护问题。

## 一、会影响编辑状态或计算结果的问题

### 1. 保存会跳过已经进入队列、但尚未执行的编辑

**级别：P1｜分类：无效逻辑、执行顺序冲突**

**位置：**

`src/features/application/graphEditing/saveGraph.ts`
`src/features/application/graphEditing/graphEditCoordinator.ts`

问题出在两个动作的顺序：

```text
saveGraph：
先 beginSave()，把 saving 设置为 true
再把保存任务放入 graphTaskQueue

applyDraftMutation：
任务真正开始时检查 saving
如果为 true，直接返回 { status: "saving" }
```

因此，“在保存之前已经接受的编辑”也会被保存标志挡住。共享队列本来应该保证先编辑、后保存，但这个提前设置的状态破坏了队列顺序。

我按源码的队列控制流做了独立复现：

```text
编辑 A：已经开始，等待后端返回
编辑 B：已经入队，等待 A
保存：设置 saving=true，然后排在 B 后面

实际结果：
A → applied
B → saving，未执行
保存 → 只包含 A
```

**建议修复：**把保存视为队列中的一个屏障：先执行完此前已经接受的编辑，再进入实际保存状态。“是否接受新的编辑”和“此前的编辑是否允许继续执行”不能使用同一个晚检查条件。

这不是 IPC 丢包，而是**前端主动跳过了任务**。[独立复现脚本](sandbox:/mnt/data/yssbi-audit-checks/queue-order.cjs)

### 2. WLS、GLS 的总平方和计算错误，会影响 R² 和 F 统计量

**级别：P1｜分类：重复逻辑中的共同错误、计算逻辑错误**

**位置：**

`src-tauri/crates/yss-sci/src/regression/linear_model/wls.rs`
`src-tauri/crates/yss-sci/src/regression/linear_model/gls.rs`

WLS 先计算：

$$
z_i=\sqrt{w_i}\,y_i
$$

然后在含截距时，以 **`z` 的普通均值**计算总平方和：

```rust
let z_mean = z.iter().mean();

z.iter()
    .map(|v| (v - z_mean).powi(2))
    .sum()
```

GLS 也对变换后的因变量直接减普通均值。两者都有同一种问题：**数据经过加权或白化后，原来的截距向量也发生了变换，不能继续机械地减变换后因变量的普通均值。**

对含截距的 WLS，应使用：

$$
\bar y_w=\frac{\sum_i w_i y_i}{\sum_i w_i},
\qquad
TSS_w=\sum_iw_i(y_i-\bar y_w)^2
$$

这也与 statsmodels 的实现一致；其 GLS 分支会对白化后的截距方向作相应处理。([统计模型][1])

我用下面的数据，按仓库公式重算，并与本机 statsmodels 独立对照：

```text
x       = [0, 1, 2, 3, 4]，模型包含截距
y       = [1, 2, 1, 4, 3]
weights = [1, 2, 4, 8, 16]
```

| 指标        | 按当前源码公式重算 | 正确加权公式 / statsmodels |
| --------- | --------: | -------------------: |
| R²        |  0.827362 |             0.325774 |
| 非稳健 F 统计量 | 14.377395 |             1.449548 |

更明显的反例是：把所有 `y` 加上 `100`，当前公式的 R² 会从约 `0.82736` 变成 `0.99968`。对包含截距的模型，这种平移不应该改变拟合优度。

**建议修复：**先明确 WLS/GLS 的截距基准与平方和定义，再收口公共统计量计算。不要只是抽取现有重复代码，否则会把同一个错误统一到更多模型中。

### 3. “等于”节点比较的是 Rust 枚举变体，而不是统一的 Numeric 数值

**级别：P1｜分类：类型语义与执行语义冲突**

**位置：**

`src-tauri/crates/yss-node-kernel/src/builtins/mod.rs`
`src-tauri/crates/yss-node-kernel/src/value.rs`
`src-tauri/crates/yss-node-catalog/src/builtin.rs`

相等判断目前直接使用：

```rust
inputs.first() == inputs.get(1)
```

而 `RuntimeValue` 使用派生的 `PartialEq`，其数值分别保存在：

```rust
Integer(i64)
Unsigned(u64)
Decimal(f64)
```

这意味着：

```text
Integer(1) 与 Decimal(1.0) → 不相等
Integer(1) 与 Unsigned(1)  → 不相等
```

但当前类型系统把这些表示归入相同的 `Numeric` 语义，`coerce_to(Numeric)` 也会保留整数表示，并不把它们全部统一为一种枚举变体。相等节点的输入协议则是共享泛型，而不是“必须具有相同 Rust 枚举变体”。

**问题本质：**Semantic 已经统一，执行比较仍然依赖 Physical 的内部表示。

**建议修复：**给数值比较提供统一的、表示感知的比较实现。这里不需要引入全局 epsilon；应先保证整数、无符号整数、浮点数之间的精确数值比较规则正确。

### 4. 大小比较强制经过 `f64`，导致合法的大整数无法比较

**级别：P2｜分类：执行能力与类型契约不一致**

**位置：**

`src-tauri/crates/yss-node-kernel/src/builtins/mod.rs`

`compare_numeric()` 对 `<`、`<=`、`>`、`>=` 都调用 `numeric_input()`。后者只允许能够无损表示为 `f64` 的整数通过，否则返回 `InvalidNumericInput`。

例如：

```text
9007199254740993 < 9007199254740994
```

这是完全合法的 `i64` 比较，但左侧数值无法无损转为 `f64`，当前路径会拒绝执行。

这里**防止精度丢失的检查本身是对的，错误在于整数比较不该被迫经过浮点转换**。项目已有保留整数的运行值和整数算术路径，因此这个限制不来自统一的数值契约。

**建议修复：**整数之间直接比较；混合表示再进入明确的数值比较规则。与上一项一起处理，但不要用“全部转成 `f64`”来修复相等判断。

### 5. 多个模型把判秩失败转换为“秩为零”

**级别：P1｜分类：错误吞掉、重复的错误处理逻辑**

**位置：**

`yss-sci/src/regression/collinearity.rs`
`yss-sci/src/regression/linear_model/prais.rs`
`yss-sci/src/regression/linear_model/wls.rs`
`yss-sci/src/regression/linear_model/gls.rs`

这些路径使用：

```rust
matrix_rank(...).unwrap_or((0, f64::INFINITY))
```

但底层 `matrix_rank()` 明确把分解失败作为 `LinalgError` 返回。**分解失败与成功计算得到零秩，不是同一件事。**

后果不只是错误信息不准确：

* 共线性处理中，可能把失败的判秩结果用于继续删列。
* WLS、GLS 接着计算 `rank - 1`。当启用截距且回退为零秩时，会进入无符号减法下溢路径，而不是正常返回模型错误。
* 依赖秩的自由度与后续统计量也失去了可信依据。

**建议修复：**统一传播判秩错误，再分别处理真正的零秩、秩不足、自由度不足。不能仅把 `rank - 1` 改成 `saturating_sub(1)`，那只会继续掩盖根因。

### 6. 判秩容差的乘法顺序存在中间溢出

**级别：P2，极端量级输入｜分类：数值实现错误**

**位置：**

`src-tauri/crates/yss-sci-linalg/src/lib.rs` → `matrix_rank()`

当前计算：

```rust
let tolerance = largest * rows.max(cols) as f64 * f64::EPSILON;
```

当最大奇异值很大时，前两项可能先溢出，之后再乘很小的 epsilon 已经无法恢复。

独立算术检查的结果是：

```text
largest = 1e308
max(rows, cols) = 2

当前顺序：
(1e308 × 2) × EPSILON → Infinity

调整顺序：
1e308 × (2 × EPSILON) → 4.4408920985e292
```

一旦容差变成无穷大，有限奇异值就无法通过 `value > tolerance`，会被错误判成零秩。

**建议修复：**先计算相对容差因子，再乘最大奇异值，并明确非有限结果的错误策略。这是表达式层面的确定问题；我没有运行该仓库 SVD 对极端矩阵的完整端到端验证。

### 7. Prais 把“达到迭代上限”当成“已经收敛”

**级别：P1｜分类：无效逻辑、结果状态失真**

**位置：**

`src-tauri/crates/yss-sci/src/regression/linear_model/prais.rs` → `Prais::fit()`

当前代码：

```rust
let converged =
    (rho - rho_old).abs() < self.config.tol
    || iterations >= self.config.max_iter;
```

之后直接进入 `Ok(PraisResult { ... })`，结果中没有区分“满足收敛条件”和“耗尽迭代次数”的状态。

按源码残差与 `rho` 更新公式构造的小样例，在：

```text
max_iter = 1
tol = 1e-12
```

时，首次 `rho` 变化约为 `0.96262`，明显没有达到容差要求，但当前条件仍然把它判为 `converged=true`。

**建议修复：**分离收敛判定与停止原因。可以返回未收敛结果并明确标记，也可以按模型契约报错，但不能静默地作为正常收敛结果返回。

### 8. Settings 全量跨窗口同步会覆盖另一个窗口尚未保存的修改

**级别：P2｜分类：多写入方冲突、状态覆盖**

**位置：**

`src/features/core/settings/settingsStore.ts`
`src/features/application/settings/settingsSyncCoordinator.ts`
`src/services/platform/settingsEvents.ts`

当前实现同时具备三个条件：本地修改防抖 `500ms` 后保存；广播完整 `AppSettings`；接收远端设置时整体替换 `ai` 和 `appearance`。

可以形成下面的覆盖顺序：

```text
窗口 A：修改 AI 模型，尚未到防抖保存时间
窗口 B：修改主题，广播完整设置，其中仍包含旧 AI 模型
窗口 A：接收 B 的完整设置，覆盖自己的新 AI 模型
窗口 A：防抖保存触发，读取的是已经被覆盖的状态
```

我对这一数据流做了独立复现，A 的待保存修改确实会消失。

**建议修复：**选择单一的设置提交入口，或传递字段级修改并处理本地未提交字段。仅增加一个全局 revision 并不能自动合并两个窗口对不同字段的修改。

### 9. 两个 Graph 前端 Store 对旧快照的接纳规则不同

**级别：P2，高可信静态一致性风险｜分类：多份镜像准入冲突、重复协调逻辑**

**位置：**

`src/features/core/graphEditing/graphEditingStore.ts`
`src/features/core/dataStore/graphProjectionStore.ts`
`src/features/application/editorMutation/projectPublicationSnapshot.ts`

`graphEditingStore.installSession()` 会拒绝同一会话的旧 revision：

```text
当前 revision > 输入 revision → 保留当前状态
```

但 `graphProjectionStore.replaceProjection()`、`commitPreparedGraphProjectionReplacements()` 没有对应的版本接纳判断，会安装传入的投影。

项目快照提交路径先设置规范化投影，再调用编辑 Store 的 `hydrate()`。准备投影与提交之间存在异步等待，而提交前主要重新过滤 `dirty/saving`，没有统一确认这份 Graph 会话快照是否已经落后。

因此，对同一份旧输入，可以出现：

```text
编辑 Store：拒绝旧快照，保留 v11
画布投影 Store：安装旧快照，变成 v10
```

**这不是“有两份数据就一定违反单一事实源”，而是两份派生镜像作出了不同的接纳决定。** 后端权威文档未必受损，但前端可能出现编辑依据与画布显示不一致。完整桌面竞态仍需验收。

此外，投影安装步骤散落在 `graphEditCoordinator`、`graphProjectionLifecycle`、`refreshGraphProjection`、`saveGraph` 中，更新顺序及 dirty/stale 发布动作不完全相同，这增加了继续漂移的风险。

**建议修复：**收口一个会话快照接纳与提交流程，先决定接纳或拒绝，再更新所有相关投影；不要让每个 Store 分别决定。

### 10. Settings 的运行时校验没有真正保证 `AppSettings` 类型

**级别：P2｜分类：无效校验、类型契约漂移**

**位置：**

`src/services/platform/settingsEvents.ts` → `isSettingsPayload()`

这个类型守卫只检查顶层有 `ai`、`appearance` 两个对象，没有验证内部字段，却声明返回值能保证 `AppSettings`。

例如下面的数据会通过：

```json
{
  "ai": { "openAiApiKey": 123 },
  "appearance": {}
}
```

但 `openAiApiKey` 的正式类型是 `string`，而 `mergeSettings()` 使用 `??` 补默认值，并不会把数字 `123` 拒绝或修正。因此错误类型会被包装成“已经验证的设置”进入 Store。

**建议修复：**为本地读取和跨窗口消息使用同一份字段级解析规则。区分“字段缺失，可以补默认值”和“字段类型错误，应拒绝”，避免维护两套强弱不同的校验。

### 11. 节点目录与实际可执行能力之间仍有明确缺口

### 14. Harness 仍在执行旧格式迁移，与当前根规则冲突

**级别：P2 架构清理｜分类：兼容逻辑残留、规则与代码冲突**

**位置：**

`src-tauri/crates/yss-harness-sqlite/src/migrations.rs`
`src-tauri/crates/yss-harness-sqlite/src/lib.rs`

这不是历史文档，也不是无人调用的迁移文件。启动连接会进入 `ensure_schema()`，读取 `PRAGMA user_version`，然后实际调用 `migrations::migrate()`。

仍在执行的迁移包括：删除旧 `operationId`、把 `compile_graph` 改成 `validate_graph`、改写旧结果与错误名称、删除 `artifactId`，以及修改历史 diagnostics 前缀。迁移还涉及工作流、授权记录和技能能力声明。

而本次提交的根规则已经要求当前未发布阶段不要维护旧数据、旧类型或旧 schema 的兼容迁移。这两者直接不一致。

**建议处理：**按照你当前“不兼容旧格式”的方向，明确旧 Harness 数据库的拒绝或重建策略，然后删除迁移调用及对应改写逻辑。不能只删 `migrations.rs`，却保留一条看似支持旧版本的初始化路径。

另外，Settings 中仍有旧存储键删除逻辑。它只是清理旧键，**不是兼容读取旧设置**；可与此轮存储策略统一整理，但优先级低于 Harness 的实际迁移。

### 15. 有几处无效判断和无意义的矩阵复制

**级别：P3；其中保护逻辑应重新设计｜分类：无效逻辑、重复计算**

| 位置                | 具体问题                                                        | 处理方向                        |
| ----------------- | ----------------------------------------------------------- | --------------------------- |
| `prais.rs`        | `rho` 已被限制到 `[-0.999, 0.999]`，之后却检查 `sqrt(1-rho²) <= 1e-10` | 对有限数值，这个错误分支不可达；应重新确定边界处理策略 |
| `collinearity.rs` | 先判断 `rank == keep.len()`，紧接着又判断 `rank >= keep.len()`        | 条件重复，可合并，并明确异常秩结果的处理        |
| `collinearity.rs` | `Mat::from_fn()` 构造拥有数据的矩阵后，又立即 `as_ref().to_owned()`       | 删除不必要的整矩阵复制，直接借用已有矩阵        |

Prais 的问题尤其不能靠删除错误分支就算完成：在现有截断范围内，`sqrt(1-rho²)` 最小约为 `0.04471`，离 `1e-10` 很远。**代码看起来有“不稳定变换保护”，实际上这个保护条件不起作用。**
