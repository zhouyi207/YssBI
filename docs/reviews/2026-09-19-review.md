**有，而且有几处值得优先优化。我的判断是：目前节点系统的大方向已经比较合理，最需要改的不是继续拆 crate 或引入 ECS，而是减少节点间的数据复制、补齐统计内核的资源控制，以及完善节点定义和内核之间的契约。**

我检查的是 `main` 的 **`a8f3b74` 提交，提交日期为 2026 年 9 月 19 日**，涉及节点协议、注册、目录、内核，以及 Graph Execution 的调用和数据传递链路。以下是静态代码审查，未运行测试或性能基准，因此会区分“代码中已经确认的问题”与“需要基准验证的优化”。

## 一、最值得优先改：节点之间传递内存数据时，存在多次深复制

**这是我看到的最明确、也最值得先处理的性能问题。**

主要位置：

```text
yss-node-kernel/src/value.rs
yss-graph-execution/src/state.rs
yss-graph-execution/src/result.rs
yss-node-kernel/src/builtins/statistics.rs
```

### 现在的问题

`RuntimeValue` 使用了：

```rust
#[derive(Clone, Debug, PartialEq)]
pub enum RuntimeValue {
    // ...
    List(Box<[RuntimeValue]>),
    Record(BTreeMap<Box<str>, RuntimeValue>),
    // ...
}
```

因此，对于 `List` 和 `Record`，调用 `clone()` 会复制其中的内容；并不像 `SeriesHandle`、`RelationHandle` 或 `Arc<LinearRegressionResult>` 那样主要是复制共享引用。

而执行调度器中存在连续的复制：

| 阶段            | 当前操作                               | 对内存数列的影响 |
| ------------- | ---------------------------------- | -------- |
| 下游节点读取上游输出    | 从 `values` 中 `.cloned()`           | 再复制一份输入  |
| 当前节点保存输出到执行槽位 | `slot.replace(value.clone())`      | 复制输出     |
| 当前节点保存可查询结果   | `StoredResult::new(value.clone())` | 又复制一次输出  |

这些调用在实际执行链路中，不只是测试代码。一个较大的内存数列经过多个节点，或者连接到多个下游时，会产生额外的整列复制。

**而且，项目已经有 `Arc<StoredResult>` 形式的结果快照，但共享发生得比较晚：进入快照之前，上述复制就已经发生了。** 所以这里不是需要重新做一个 ResultStore，而是要把共享边界前移。

### 建议分两步改

**第一步：先去掉明显不必要的复制。**

例如，调度器已经把一份值放入执行槽位之后，构造 `SchedulerResult` 时可以移动原值：

```rust
results.push(SchedulerResult {
    value: StoredResult::new(value), // 移动，不再 clone
    category: output.contract().category,
    output: output.output().clone(),
});
```

这只是局部优化，仍然保留槽位里的那次复制，但改动范围小。

**第二步：让执行槽位、结果存储和下游输入共享不可变数据。**

我建议的原则是：

> 标量按值传递，大型数据通过共享缓冲或句柄传递；需要转换时才产生新数据。

可以先让调度器和结果存储共享不可变的运行值，再让 `KernelInvocation` 借用输入视图。之后再逐步把大规模数值序列从“逐元素 `RuntimeValue`”改为有明确物理类型的共享列缓冲。

这不需要把 Arrow 或 DataFusion 的具体类型直接暴露给每个 Kernel，也不需要改变你面向用户的 `DataSeries<Numeric>` 类型。

### 统计输出也有同类问题

`statistics.rs` 中，拟合完成后有：

```rust
let fitted = numeric_list(result.fitted.clone())?;
let residuals = numeric_list(result.residuals.clone())?;
```

模型本身仍保留原始拟合值、残差数组，两个输出又分别复制并转换为 `RuntimeValue::List`。**这两个输出更适合共享模型已有的只读列缓冲或字段视图。** 相比之下，Summary 中的模型 `Arc::clone` 已经是合理做法，不应把所有 `clone()` 都一概删除。

## 二、统计节点的预算检查和取消检查，需要补齐

主要位置：

```text
yss-node-kernel/src/builtins/statistics.rs
```

这里不是完全没有资源控制，而是**不同节点之间的控制质量不一致**。

### 1. 部分预算检查发生在分配之后

`columns()` 的内存数列分支，先执行：

```text
RuntimeValue::List
    → numeric_series()
    → 收集为 Vec<Vec<f64>>
    → 检查总字节数
```

也就是说，先把全部数值转换并分配出来，再判断是否超过 `max_input_bytes`。这种检查可以拒绝继续计算，却不能阻止前面的超预算分配。

建议改成：

```text
检查列数与长度
    → checked_mul 计算所需空间
    → 检查预算
    → 预留空间
    → 分批转换，并检查取消
```

对于未知长度的流式输入，则应在读取过程中累计预算，而不是要求所有输入都提前知道长度。

### 2. 输入预算不等于峰值内存预算

当前统计准备主要用 `行数 × 列数 × 8` 衡量数值缓冲，但输出转换为 `RuntimeValue::List` 后，存储的是枚举元素，不是紧凑的 `f64` 数组。

GLS 已经检查了 `n × n × 8`，这值得保留；但响应变量、解释变量、协方差矩阵及其转换结果分别通过检查，并不意味着它们同时存在时的总占用也在同一个上限内。

建议至少明确区分输入物化、临时工作区和输出物化的预算含义。先统一公共检查方法即可，**不必立即引入复杂的全局内存管理框架**。

### 3. 长循环里的取消检查不足

`LinearPredict` 的预测循环、内存列转换，以及 `numeric_list()` 的输出转换，没有像算术节点那样周期性检查取消。执行前后检查只能保证“最终发现取消”，不能保证长时间处理期间及时响应。这里说的是这些准备、预测和转换循环，不是说 SCI 内部完全没有取消机制。

项目已有可复用的实现：`numeric.rs` 会在分配前检查输出空间、使用 `try_reserve_exact`，并在逐行计算时每隔一段检查 `check_control()`。**把统计节点向这套模式统一，比另起一套控制机制更合适。**

## 三、Kernel 错误信息过于粗糙，实际原因被丢掉了

主要位置：

```text
yss-node-kernel/src/error.rs
yss-node-kernel/src/builtins/statistics.rs
yss-node-kernel/src/builtins/relational.rs
```

现在很多不同问题最终都落到：

```rust
KernelError::Failed
KernelError::InvalidNumericInput
```

例如，统计内核把 `ScientificComputationError::InvalidInput { .. }` 转成 `InvalidNumericInput`，丢掉具体原因；关系内核又把输入无效、数列行域不一致合并成同一类错误。

这会让上层难以区分：

“列长度不同”“参数配置错误”“数列没有对齐”“预算超限”“算法数值失败”。

### 建议

保留稳定、结构化的错误类别，例如 `InputArityMismatch`、`ShapeMismatch`、`InvalidParameter`、`UnalignedSeries`、`BudgetExceeded`、`ScientificFailure`，并保留必要的底层错误来源。

**但不要把 Graph 的 `NodeId` 塞进 KernelError。**

Kernel 只描述计算错误；Execution 再补充节点身份、执行阶段和端口位置。你目前已经有这条边界，应当增强信息保留，而不是破坏分层。

这项优化不仅帮助调试，也有利于前端和 AI 工具调用方判断：应该让用户修改输入，还是减少数据量，还是停止重试。

## 四、节点定义与 Kernel 的绑定契约，还缺少输入布局

主要位置：

```text
yss-node-kernel/src/registry.rs
yss-node-kernel/src/invocation.rs
yss-application/src/session/components.rs
```

当前 `KernelContract` 主要检查：

```text
参数 key 集合
输出数量范围
```

`NodeComponents::new()` 也主要根据这两部分验证定义与实现的一致性。执行时会检查输入值数量与 `input_templates` 数量一致，但这不等于验证输入符合某个 Kernel 的实际输入契约。

与此同时，`KernelInvocation` 对固定输入没有携带模板名，部分内核依赖 `inputs.first()`、位置解构等约定；可重复输入则根据字符串模板名重新分组。

**目前我没有确认已经发生输入顺序错配，但现有契约无法充分防止这类扩展回归。** 比如两个同类型的固定输入语义不同，单靠数量和运行值类型并不能说明它们绑定正确。

### 建议

补充一层很薄的内核输入布局声明：

```text
固定输入：稳定槽位及名称
重复输入：组名、最小/最大数量
可选输入：存在条件或准备后的可选槽位
输出：稳定槽位或动态输出布局
```

在装配或准备阶段把定义中的端口映射到内核槽位，运行时只读取准备好的布局。

这里要守住一个原则：

> **验证调用约定，不是在 Kernel 中复制一套 Graph 类型推导。**

Semantic、Schema、动态端口解析仍然由 Graph 所有者负责；Kernel 不重新读取连接关系，也不重新猜输出类型。

## 五、语义指纹仍然包含部分展示字段，会造成不必要的失效

主要位置：

```text
yss-node-registry/src/fingerprint.rs
yss-node-protocol/src/model.rs
```

当前 `canonical_semantic_protocol()` 已经排除了顶层 `catalog`，但仍把完整的 `interface` 和 `parameters` 放入语义编码中。

而 `PortSpec` 里还有 `title`。因此，**仅修改端口显示标题，也会改变当前协议的语义指纹**；参数中的文案 key 等字段同样需要审查。这里不是说所有本地化文本内容都必然进入了语义哈希。

### 建议

分别建立明确的编码规则：

| 身份   | 应覆盖的内容                     |
| ---- | -------------------------- |
| 语义身份 | 类型、默认值、约束、端口绑定、动态端口规则、执行行为 |
| 展示身份 | 标题、说明、目录位置、图标及纯展示配置        |

不要直接序列化整个定义结构来充当语义编码，也不要粗暴排除所有编辑配置：会影响合法性或值绑定的内容，仍然需要参与语义身份。

这项可以先做，不必等待整体组件化完成。修改编码时应推进编码版本，并增加“只改展示不影响语义”“改类型或默认值必须影响语义”的验证。

你在 `NODE_REFACTOR_REQUIREMENTS.md` 中已经明确提出了这个方向，但它目前仍属于待落实的迁移要求，不应视为已经完成。

## 六、组件化可以继续推进，但重点应是独立契约与复用，而不是增加层数

目前已经有 `NodeInterfaceProtocol`、`ParameterSchema` 等独立类型，这并不是一个完全没有结构的节点对象。

不过，`core_nodes/support.rs` 的 `protocol()` 仍同时组织节点展示、端口、参数、执行策略和默认类型行为；不同节点再修改 `typing`、消费模式等字段。例如算术节点就是先构造协议，再补上相应的类型规则和部分执行配置。

### 我建议的收敛方向

继续沿着你已经写下的独立组件目标推进：

```text
Ports       拥有端口契约
Parameters  拥有参数契约
Data        声明数据访问与物化要求
Kernel      绑定执行实现
Operators   绑定编辑、解析行为
Catalog     拥有节点级展示信息
```

组件先独立构造、校验，再通过节点定义装配。**不要只是给原来的大对象换一个 Builder，也不要让每个节点再创建自己的数据仓库、编辑器或服务容器。** 这也符合当前重构文档的要求。

复用应优先发生在真正重复的方法族内部，例如统一数值运算的形状规则、输入布局、预算检查；统计节点则复用列准备、配置解码和结果包装。

目前已经存在算术方法族、统一线性回归内核等组织方式，应该继续增强这种复用，而不是退回“每个物理类型、每个方法复制一套节点实现”。

## 七、两项较低优先级的优化

### 1. 把静态调用信息提前准备

`kernel_invocation::invoke()` 每次调用都会重新收集输入模板、构造输出契约、复制 Schema 字段，并创建参数映射。参数本身已经通过 `Cow` 借用了部分 literal 和资源值，这部分设计是好的；可以进一步减少的是静态元数据的重复装配。

建议在执行准备阶段生成可复用的调用布局，运行时主要绑定输入和当前运行的参数、资源。

**不要顺便把资源授权长期缓存进去。** 静态布局可复用，授权绑定仍应遵守当前运行和会话边界。

这项对大量轻量节点可能更有意义；相对于大型统计计算，收益大小需要基准验证，优先级低于深复制问题。

### 2. 去掉动态字符串对 `Box::leak` 的依赖

`core_nodes/support.rs` 中存在：

```rust
pub(crate) fn leak(value: String) -> &'static str {
    Box::leak(value.into_boxed_str())
}
```

动态生成的节点标识、本地化 key 等通过这种方式满足 `'static` 接口要求。这些分配不会在相应节点系统释放时回收。

更合适的是让运行时生成的元数据拥有 `Box<str>`、`String` 或 `Cow<'static, str>`，静态常量则继续借用。

不过，这不应夸大成“每次编辑或切换项目都在泄漏”：当前 `NodeComponents` 已经共享不可变注册信息，并设计为跨项目会话替换复用。它更适合作为构造生命周期与可维护性清理项。

## 我建议的实施顺序

| 顺序 | 改动                       | 验收重点                        |
| -- | ------------------------ | --------------------------- |
| 1  | 去掉输出冗余克隆，前移结果共享边界        | 大数列连接多个下游时，不按连接数复制整列        |
| 2  | 补齐统计节点预算和取消检查            | 超预算在大分配前拒绝；长循环能及时响应取消       |
| 3  | 保留结构化 Kernel 错误          | 长度、行域、配置、预算、数值失败能明确区分       |
| 4  | 完善输入布局契约                 | 定义与 Kernel 的输入槽位、分组不一致能尽早发现 |
| 5  | 分离语义与展示指纹                | 展示变化只刷新展示，不无故改变执行身份         |
| 6  | 完成独立组件装配，复用方法族公共逻辑       | 新增同类节点不再复制通用处理流程            |
| 7  | 静态调用信息预准备、清理 `Box::leak` | 用基准确认收益，并检查构造、释放行为          |

**总的来说，我建议保留现在“Graph 负责解析、Kernel 负责计算、Execution 负责调度和结果生命周期”的结构。优先把大型数据改为共享不可变传递，把统计节点的预算、取消、错误处理补齐，再完成节点声明的组件化。这样改，比继续增加 crate、trait 或注册层更能直接改善当前实现。**
