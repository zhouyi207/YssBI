# YssBI 组件化架构重构计划

> Status: Planned
> Scope: 核心业务组件边界、Chart 独立归属、Graph Execution 内聚、应用会话整理、重复与无效代码审计清理，以及由编译和结果缓存驱动的图状态与验收
> Canonical owners: 本文拥有待实施计划；代码、测试和 Cargo manifests 拥有当前实现事实；已实现架构由现有专项文档维护
> Update when: 组件边界、阶段范围、依赖关系或验收条件改变时

本文基于 2026-09-14 检查的 `769f8d72`，承接 [组件化讨论](component.md)。已确认的设计方向是：Node 与 Chart 作为一级业务组件，Execution 在业务上归入 Graph，应用会话继续独立于 Graph；保留结果缓存及报告租约，删除无生产路径的执行遗留，以编译事实和缓存有效性驱动连线、Pin 与图中节点状态。除第 9 节明确勾选的事项外，以下目录、接口和行为安排仍为目标。

实施时先检查最新代码与规则。每个阶段完成后，将实际形成的契约更新到对应 Current 文档；本文只维护计划状态与剩余工作，不替代当前架构说明。

## 1. 目标与范围

目标是形成可长期扩展的组件化模块单体。一个组件由明确的业务职责、状态所有权、公开 API、依赖和生命周期定义；组件可以由多个 crate 或模块共同实现。

完成后应能观察到：

- Application 按业务用例组织代码，组件拥有领域规则和内部状态。
- 修改组件内部实现时，无关组件不需要跟随修改。
- 新增使用既有类型和语义的节点、图表类型或数据源时，改动集中在对应能力及注册位置。
- 跨组件提交、会话切换、失败补偿和结果失效仍能从用例中直接追踪。
- 桌面、Harness 和插件宿主适配通过相同业务入口工作，不建立平行实现。

目录和组件整理以行为保持重构为主；下述已确认的功能删除、缓存失效与图状态改造先单独实施，扩展接口改造另成阶段。不预设 crate 数量目标，不同时更换数据引擎、持久化格式或异步执行方式。IPC 和前端投影只调整这些明确需求涉及的部分，不引入通用组件容器、按字符串查找服务的注册中心或统一 JSON 业务调用接口。

### 1.1 已确认的保留、删除与改造

| 对象                                   | 决定               | 范围                                                                                                  |
| -------------------------------------- | ------------------ | ----------------------------------------------------------------------------------------------------- |
| 结果记录、当前输出缓存和报告租约       | 保留               | 业务名称使用“结果缓存与持有租约”，不称为“历史快照”；已打开报告继续读取打开时的不可变结果              |
| 执行录制、回放及旧动画事件队列         | 删除并替换呈现依据 | 删除录制数据、回放控制和无生产者的逐节点动画队列；保留动画需求，改由真实编译、运行及缓存状态驱动      |
| `StoredResult::Scalar/Text/Empty`      | 删除               | 统一使用已有 `RuntimeValue`；保留输出类别、结果身份、原生数据及只读查询能力                           |
| `PlanValidationControl`                | 暂时保留           | 当前是 Graph Execution 的计划校验控制对象，尚未接入；不因 Harness 可以提供预算就转移其领域归属        |
| Graph 的 stdout/stderr Run Output 管线 | 删除               | 当前没有 Print 节点或正式生产者，连同专用消息、映射、缓存和空展示路径一起删除；保留运行失败摘要及定位 |

此前审查提到的函数执行包、`recursion_limit` 和 RunRegistry 终态清理作为第 1.2 节的审计候选，核实实际责任和调用方后再决定处置，不把候选直接当成无效代码。第 1.1 节明确保留的结果租约和 `PlanValidationControl` 等继续保留。Harness 自己的 turn/workflow 事件、回放恢复与插件进程通信不属于本次 Graph 执行录制及 stdout/stderr 清理。

### 1.2 贯穿各阶段的逻辑审计与清理

每个阶段都检查受影响组件及其完整调用链，发现问题后在对应职责归属内修复并清理旧路径。这是本计划的实施要求，不仅是最终审查建议。按实际问题选择最小、清晰且有效率的实现，不为完成清理另建通用框架。

| 检查项                | 检查依据                                                                                                                | 处理要求                                                                                                                                 |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 重复逻辑              | 同一业务规则、校验、类型转换、状态推导或资源访问是否由多个位置分别实现；看语义、生命周期和提交时机，不只比较文本        | 交回唯一职责归属并复用已有入口，移除重复实现；保留信任边界校验和提交前重验等有独立目的的检查                                             |
| 无效逻辑              | 不可达分支、永远为空的生产路径、无效果的状态写入、无消费者的数据、已经取消需求的占位实现                                | 确认没有实际行为后成套删除生产、传输、缓存、订阅与展示路径，保留仍在使用的共享部分                                                       |
| 代码漂移              | 实现、声明、DTO/parser、注册表、测试、文档和生成索引是否表达同一契约；新旧版本是否分别修补同一个问题                    | 以源码、实际调用和测试核实事实，修正漂移的责任方及受影响消费者；生成内容通过原生成入口更新                                               |
| 多事实源              | 同一已提交事实、缓存有效性或运行状态是否存在多个可独立写入的权威；是否靠双向同步或互相补写保持一致                      | 明确唯一权威和单向投影，删除平行存储与补同步逻辑；显式草稿、必要的边界 DTO、不可变读取视图和只读缓存不因形似而合并                       |
| 代码冲突              | 未解决的 Git 冲突，以及新旧入口并存、重复注册、状态回写、取消/失效/提交顺序相互覆盖等语义冲突                           | 统一执行入口和生效顺序，处理相关冲突并检查所有调用方；保留用户无关改动，不通过覆盖文件或忽略错误掩盖冲突                                 |
| 无效函数              | 函数、方法、导出、命令或回调是否存在真实可达调用；同时检查注册表、宏、trait 实现、feature、测试支持、Harness 和插件适配 | 确认为无效后删除定义、导出、注册、调用残留与不再需要的依赖；仅搜不到前端引用或编译器没有告警，均不足以得出结论                           |
| deprecated 与兼容逻辑 | 废弃 API、旧命名重导出、旧 DTO、版本分支、兼容包装和 fallback 是否仍有必须支持的消费者                                  | 0.x 内部旧路径直接迁移调用方并删除，不新增长期兼容门面；确需支持的持久化格式或独立插件协议按既有契约处理，明确适用版本、责任方和退出条件 |

实施时遵循以下顺序：

1. **沿生产路径核实问题**：从桌面、Harness、插件或其他已支持入口追踪到业务 owner、数据读写和结果消费者，区分正式路径、测试构造、显式暂留项和真正遗留。确认职责、失败语义及所有权后再决定合并或删除。
2. **记录可核查的处置依据**：每项问题记录代码位置、调用证据、影响行为、唯一职责归属、拟删除/复用/重构内容与验证方式。证据不足的项保留为未决事项，不报告为已解决；明确保留的项写清理由，不反复作为待删项。
3. **优先整理已有实现**：优先直接复用、内聚和缩小公开面，必要时在现有组件内提取有真实职责的逻辑。避免为共享几行代码新增 crate、单实现接口、无状态门面、全局容器或另一套模型。
4. **同时检查执行成本**：关注重复 Resolve、全图遍历、全量克隆、重复 I/O、重复投影计算和过大的锁范围；复用安全的已捕获事实与有界查询，保留会话、资源版本和最终提交重验。有性能改进结论时用代表性场景验证，不以“代码更少”代替效率证据。
5. **迁移与删除一起完成**：同一迁移单元同步更新调用方、导出、注册、DTO/parser、依赖、测试、文档和相关生成入口，随后移除旧实现。按第 10 节执行受影响范围的验证，不能只加一条新路径而让重复路径继续生效。

审计清单与每阶段实施记录一起维护即可，不新建通用审计系统或复制仓库级规则。判断“干净”的依据是职责唯一、调用清楚、状态来源明确、旧路径已清除且行为得到验证，不以 crate 数量、文件大小或零告警作为完成标准。

## 3. 目标业务组件

下面是业务分解树，不是 Cargo 依赖图，也不要求每个节点对应一个 crate。

```text
Application                         统一入口、组装、会话与跨组件用例
├─ Project                          项目、资源与持久化
├─ Database                         数据访问、查询和编辑
├─ Node                             节点协议、定义、注册与目录
│  ├─ Protocol                      端口、参数、类型与语义声明
│  ├─ Registry                      注册、校验与能力指纹
│  └─ Catalog                       内置定义、分类、创建描述与文档
├─ Graph
│  ├─ Document / Editing            图文档规则与编辑
│  ├─ Analysis / Compilation        语义分析与编译
│  └─ Execution
│     ├─ Kernel / Scheduling        节点计算与调度
│     ├─ Runs / Cancellation        运行与取消
│     └─ Results                    图结果及其生命周期
├─ Chart                            图表声明、绑定和展示规则
├─ Harness                          自动化会话与任务
└─ Plugins                          独立扩展及宿主管理
```

### 3.1 职责与状态所有权

| 组件或协调层 | 拥有的事实与规则                                       | 公开能力                                     | 保留的边界                                                                |
| ------------ | ------------------------------------------------------ | -------------------------------------------- | ------------------------------------------------------------------------- |
| Project      | 已提交项目、资源声明、资源版本、文件事务、提交权限     | 读取事实，加载资源，准备与提交资源变更       | 数据库查询、图编译和图执行由各自组件完成                                  |
| Database     | 数据访问、查询、数据编辑、数据库运行态和物理变更       | 有界查询，捕获快照，准备、提交及补偿变更     | Project 继续拥有数据库资源声明和项目提交权限                              |
| Node         | 节点定义、端口与参数协议、注册表、目录                 | 注册校验，冻结定义，查询节点与目录           | 图中节点实例、连接后的类型和语义归 Graph                                  |
| Graph        | 图文档规则、编辑运算、语义快照、编译产物、图运行与结果 | 解析、编辑规划、编译、运行、取消和查询图结果 | 已保存图文档归 Project；跨组件运行授权归 Application 用例                 |
| Chart        | 图表声明、编码与绑定规则、绘图输入和展示规则           | 校验声明，组织图表投影，提供图表呈现能力     | 文件事务归 Project，数据查询归 Database，图结果生命周期归 Graph.Execution |
| Harness      | 自动化会话、turn、workflow、调用记录和恢复规则         | 接收任务，通过中立能力端口调用 Application   | 不通过 Tauri 命令作为内部业务总线                                         |
| Plugins      | 安装、实例监督、任务与受控宿主能力交付                 | 加载和管理独立扩展，接收插件请求与产物       | 插件算法归插件，项目与数据提交权限留在宿主                                |
| Application  | 用例顺序、完整会话组合、身份重验、跨组件提交与恢复协调 | 提供业务入口和类型明确的回执                 | 不复制组件算法，不拥有第二份已提交领域模型                                |

Node 是组件总称，Catalog 是其中的目录能力。复用现有 `yss-node-protocol`、`yss-node-registry` 和 `yss-node-catalog`，具体 crate 保留反映职责的名称。图中节点实例、连线、解析后的语义和画布状态归 Graph；节点的实际 kernel 实现与调度归 Graph.Execution。文中呈现规则里的 Node 指图中节点，不代表 Node 组件持有运行状态。

Chart 是跨前后端的逻辑能力：Rust 负责权威数据及相关规则，前端负责图表声明的显式编辑草稿和呈现。共享前端渲染器可以同时服务独立图表与结果窗口，不因此成为结果数据 owner。

### 3.2 Graph 内部 Execution 的归属

- 业务上将 Execution 归入 Graph，明确为图执行子系统。
- 首轮保留 `yss-graph-execution` 独立 crate，保留中立执行计划和受控资源接口。
- `yss-graph-runtime` 继续负责解析与编译缓存，不新增对 Execution 实现的依赖，也不持有整个应用会话。
- Graph 编译包到执行包的转换、Project 授权、资源绑定及结果发布协调仍在 Application 的图用例中。
- Graph 内的 Results 只管理图运行结果，不吸收 Database 查询状态、Harness 任务或插件产物账本。插件产物继续沿用 Project 的既有提交入口。

业务分组调整不自动改变架构门禁中的 Graph、Execution、Application 层级和依赖限制。

### 3.3 必须保持的状态边界

沿用 [Graph 与 Execution](../architecture/GRAPH_AND_EXECUTION.md) 的契约：已保存图文档属于 Project；未保存草稿及撤销历史属于前端 GraphDraftSession；解析后的类型、Schema、血缘和诊断由 GraphSemanticSnapshot 唯一拥有。

Compile、Save、Execute 保持独立。Compile 不提交文档，Save 不隐式编译，Execute 必须使用与会话、图路径和依赖匹配的编译产物。Graph Problems、运行日志、运行状态/失败和 Results 保持不同事实与生命周期。目标中移除无生产者的 Graph stdout/stderr 流；Output 面板保留运行失败摘要，不将错误改写成日志或结果值。

## 4. 组件接口与依赖规则

组件边界在已有 owner 上建立。Graph 优先完善 GraphRuntimeState；Project 和 Database 使用现有受控入口；Chart 复用 ChartDocument 与共享图表呈现能力。首轮不创建空的组件实现 crate 或新的全局状态容器。

每个组件在已有说明中明确以下契约：

| 契约项       | 应明确的内容                                       |
| ------------ | -------------------------------------------------- |
| 提供的操作   | 查询、准备、提交、取消、释放等业务动作             |
| 输入         | 类型明确的参数、不可变事实、期望版本或受控句柄     |
| 输出         | 结果、快照、提交回执或不透明标识                   |
| 状态与作用域 | 谁可修改，属于进程、项目会话还是单次操作           |
| 失败与重试   | 是否已提交，是否允许重试，如何识别原操作和恢复工作 |
| 依赖         | 允许使用哪些组件 API、共享契约和注入端口           |

具体约束：

1. 缓存、锁、连接和内部可变容器默认私有；不能通过 getter 重新开放整份内部状态。
2. 固定领域服务可以直接调用具体类型。需要替换实现或隔离资源访问时才引入窄 trait，优先复用已有端口。
3. 同一 crate 内的 `pub(crate)` 不构成组件级隔离；组件内部采用更窄可见性，并使用已有架构门禁约束调用位置。
4. 共享契约放在已有适当 owner 中。不建立汇总所有业务类型的 `common` 或 `component-contracts` 包，也不靠全量重导出掩盖实现依赖。
5. 用例可以捕获 ApplicationSession；领域组件只接收完成操作所需的事实和能力，不注入 ApplicationState 作为服务查找入口。
6. 业务错误保留分类和提交状态。IPC 继续映射为现有 Rust-owned 错误 wire；内部 API 不被统一降为字符串或任意 JSON。
7. 进程内组件 API 随 workspace 一起演进；持久化格式和独立插件协议的兼容性按现有专项契约处理。

## 5. 组装与生命周期

### 5.1 生命周期分层

| 作用域     | 典型对象                                                        | 目标规则                                              |
| ---------- | --------------------------------------------------------------- | ----------------------------------------------------- |
| 进程级     | 不可变节点定义、项目注册服务、Harness Host、Plugin Manager      | 集中组装；按各服务自己的关闭与恢复规则管理            |
| 项目会话级 | Project 会话、Database 会话、Graph 缓存、Execution 运行态和结果 | 绑定同一个完整 ApplicationSession，统一校验代次和身份 |
| 操作级     | 准入、取消控制、临时结果读取、准备好的变更对象                  | 明确截止、释放、提交或补偿路径，不能跨会话重新解释    |

报告租约属于显式消费者的生命周期：由真实面板存在或独立窗口存活决定释放，不等同于单次查询、组件挂载或面板可见性。图输出缓存由 Graph Execution 持有，并受第 6.4 节的失效、替换和回收规则约束。

节点定义可按冻结版本在多个会话间共享；资源目录、本地化查询结果和图语义缓存仍按各自输入与版本失效，不能把项目相关内容混入进程级定义缓存。

Runtime 继续选择 SQLite、Rig、文件监听器及通用插件管理实现。SCI 沿用现有规则：只有 Graph Execution 和 Application 的独立 SCI commands 消费 SCI runtime；组装层不构造或注入科学计算后端。

### 5.2 会话切换

```text
验证目标项目
    → 关闭旧会话的新操作准入
    → 等待、取消或恢复旧会话活动工作
    → 完成项目激活并构建候选会话
    → 校验组件身份与绑定关系
    → 整体发布新 ApplicationSession
```

- 一个用例只捕获一次应用会话，后续 Project、Database、Graph 与 Execution 操作都绑定该捕获。
- 保留现有候选会话、最终校验和原子发布边界，不能将各组件的“切换当前项目”变成互不协调的独立操作。
- 前置验证失败保留原会话；drain 后失败按现有协议重建可用会话或保留恢复工作，不能仅重新打开准入标志。
- 已持有旧引用的操作仍需经过最终身份与版本校验；不能把迟到结果归入新会话。
- 关闭一张图、一个结果窗口和切换项目是不同生命周期事件，不能共用无条件清空全部结果或会话的实现。

### 6.4 结果缓存、依赖失效与撤销

#### 名称和保留机制

这一能力称为“结果缓存与持有租约”。`StoredResultSnapshot` 在当前实现中是包含共享值、输出地址和 provenance 的一致性只读视图，不是历次运行归档；技术名称中的 Snapshot 不要求一律重命名，也不改变 GraphSemanticSnapshot 或数据库快照的含义。

保留 ResultStore 作为唯一结果 owner，继续使用 `{ executionSessionId, resultId }`。当前输出缓存和显式报告租约持有同一份不可变结果；最后一个持有者释放后移除记录，正在读取的临时 `Arc` 在查询结束后释放实际数据。保留分页、原生 OLS 数据与分析、跨窗口租约交接、窗口关闭清理、会话隔离及迟到请求检查。报告不会因图编辑、重跑而自动切换到另一份数据。

为满足“修改连线后下游变旧，撤销后恢复”，需要调整失效策略：**缓存是否还被持有，与缓存是否适用于当前图分开判断**。实施前 [ResultStore](../../src-tauri/crates/yss-graph-execution/src/result_store.rs) 的 `observe_graph_inputs` 在整图语义 hash 改变时解除全部输出绑定；本阶段必须替换这一行为，不能仅恢复前端颜色。

目标采用每个现存稳定输出地址一份最近成功缓存的方式。语义编辑只使受影响缓存变旧，缓存槽仍持有原结果及计算依据；它不再作为有效当前结果参与 Pin 预览、搜索或执行输入。`get_pin_result` 仍只交付有效当前结果，过期缓存信息由状态投影表达；报告通过完整结果引用读取被持有的数据。缓存由本输出重算准入、替换、显式清理、输出删除、图卸载或会话结束时释放；报告租约独立。一个输出不维护按运行次数增长的版本列表，也不把结果 payload 放入 Draft undo/redo 栈。

这个调整延长的是编辑期间现有输出缓存的持有期，不另建历史结果仓库。默认保证缓存尚未被重跑或清理时的“编辑 → 撤销”恢复；被回收或替换的旧值不从撤销栈复活。本轮改变草稿编辑的失效策略，运行准入、失败和取消沿用原有规则：重算开始解除实际 demand outputs 的旧缓存绑定，失败、取消不恢复它们为有效当前结果；未重算输出与报告租约按各自规则保留。是否有缓存与本次运行结局分别表达，失败不能显示为本次执行成功。

#### 依据与传播

- Graph 从已有语义分析权威提供 operation/端口依赖、参数、类型、coercion 和能力依据；Execution 记录本次结果实际使用的上游结果版本及资源版本。Application 完成两者映射，Graph/Node 不反向读取 Execution 内部状态。
- 结果有效性按节点/输出的实际依赖判断，不能只比较整图 `semanticInputHash`，也不能只看 Pin ID、连线 ID 或是否曾运行。数据库内容版本、函数依赖和 kernel 版本同样参与检查；无关节点编辑和布局变化不使不相关缓存失效。
- 新增、断开、重接一条边，从输入绑定发生变化的目标节点开始，沿数据依赖传播到其下游。使用编辑前后依赖关系覆盖被移除的路径；一个 operation 的相关输出一致失效。上游节点、旁路分支和无关节点保持各自状态。
- 连线的“结果有效”同时要求当前绑定与目标节点生成缓存时实际消费的输入一致。仅源 Pin 有缓存，不足以把运行后新连到它的边标为已执行。
- 上游重新产生新结果版本后，使用旧版本的下游缓存变旧，即使节点和连线 ID 未变。仅在 demand 中重算的部分发布新结果；其余节点按各自依据判断，不随全图完成事件一律变为有效。
- 缓存状态投影复用现有 Application results 与图投影入口。Rust 决定有效、过期和缺失，React 只组合投影与本地交互状态来呈现；不在前端重复实现语义解析或另存可任意写入的“已经执行”事实。

缓存状态用于展示和当前结果查询；这一步不自动引入调度器跳过 kernel 的增量求值。若后续需要计算复用，仍需在执行入口校验完整依据与 kernel 的复用条件。

#### 撤销与编译产物

复用现有 [historyCoordinator](../../src/features/application/graphDraft/historyCoordinator.ts)：撤销恢复文档后由 Rust 重新 Resolve，再计算缓存适用性。仅当语义依据、资源版本、实际输入版本和会话均匹配且结果仍存活时，恢复 Pin、连线和 Node 状态；重做再次按同一规则失效。撤销历史不保存颜色、动画播放位置或另一份执行结果。

编译状态与结果缓存状态独立。当前 [GraphDraftStore](../../src/features/core/graphDraft/graphDraftStore.ts) 在语义变化时会丢弃编译引用，而 [Graph Runtime](../../src-tauri/crates/yss-graph-runtime/src/lib.rs) 每张图保留一份编译产物。目标允许撤销后经后端核对重新关联仍匹配的已有产物；产物被后续编译替换或依赖变化时，仍要求显式 Compile。不能通过恢复 `compiled` 样式跳过产物检查，也不由 Undo 隐式重新编译、保存或执行。

全图编译状态可以阻止下一次 Execute，但不能据此统一清除未受影响子图的缓存状态。恢复了有效缓存也不等于恢复了一个仍存在且可执行的编译产物。

发布结果仍原子检查 session、依赖、run 和输出写入资格。编辑、撤销、重做产生的新请求用现有 generation/request identity 拒绝迟到回执；恢复相同语义不能重新授予已过期 run 发布结果的资格。

### 6.5 编译、缓存驱动的连线、Pin 与 Node 呈现

删除录制器后，动画由当下事实驱动，不按历史节点事件重演。编译状态、缓存适用性、当前运行状态分别保留，视图统一派生显示规则。沿用 Pin 类型底色，通过线型、强度、标记和短暂动画表达阶段，不单靠颜色辨别。

| 情况                   | 连线与 Pin 的目标表现                                        | Node 的目标表现                                    |
| ---------------------- | ------------------------------------------------------------ | -------------------------------------------------- |
| 新建或修改，尚未编译   | 细虚线和待编译标记；即使源端有结果，也不显示该新绑定已被执行 | 待编译标记；原有缓存若被影响，另标为过期           |
| 正在编译               | 本次编译范围显示短暂脉冲，结束后由回执决定样式               | 编译中的轻量提示，不表示 kernel 正在执行           |
| 编译通过，尚无匹配结果 | 清晰实线和已编译标记；与有效缓存样式区分                     | 已编译状态，不显示运行成功                         |
| 已有匹配缓存           | 稳定高亮及结果可用提示，不持续播放流动动画                   | 对应输出可用；部分结果时不能把整个节点笼统标为完成 |
| 输入变化，保有旧缓存   | 过期标记和区别于新边的断续线型；受影响下游同步变化           | 标明结果过期，上游和旁路节点保持原状态             |
| 当前 demand 正在运行   | 对本次运行涉及的依赖范围显示运行效果                         | 表示参与本次运行；终态后按实际结果投影更新         |
| 编译阻断或执行失败     | 按真实诊断位置/失败来源显示错误标记                          | 展示具体原因；仍持有的缓存信息与失败状态分别表达   |

诊断和当前活动状态优先显示，缓存标记仍可独立展示。运行效果只能反映当前事件能证明的范围；没有 scheduler 的逐节点进度事实时，不通过定时器编造节点执行先后。使用现有渲染器及 CSS 过渡/动画，遵循减少动态效果偏好，不再增加回放存储或逐帧业务队列。

示例中，`A → B → C` 与 `A → D` 都已运行。断开 `A → B` 后，A 和 A→D 的结果保持有效，B/C 及 B→C 变旧；将 X 接到 B，X→B 属于尚未执行的新绑定。撤销这些编辑且原缓存与外部依赖仍有效时，恢复 A→B、B→C 和 B/C 的状态。移动节点、重命名显示标签不影响此结论。

### 6.6 已确认遗留的删除边界

- **录制与旧动画**：执行入口、回放 hook、旧 live event 队列、执行 store、工具栏、Node/Edge renderer 及主题样式已一起迁移；回放模块已删除。共享的真实运行终态、取消、Pin 预览和渲染几何继续保留，新呈现见 [graphPresentation](../../src/features/application/results/graphPresentation.ts)；真实界面验收仍待完成。
- **重复值类型**：[StoredResult](../../src-tauri/crates/yss-graph-execution/src/result.rs) 的正常生产路径统一到 `RuntimeValue`，同步清理 Application 结果查询、分页、IPC DTO 与 Automation 检查中的旧分支。测试数据改用真实生产类型，保留空值、有限数检查、输出类别及报告投影含义。
- **stdout/stderr**：删除 Execution `run_output` 消息、无生产者回调、Application/IPC 映射、共享 DTO/parser、ProjectService `onOutput`、专用前端投影、sequence/loss 展示与对应空 UI。保留 RunStarted/Completed/Errored/Cancelled、结果通知、Channel 终态排空及错误收尾顺序；Output 面板保留运行失败摘要和节点定位，清除该摘要不清除 Results。
- **校验控制**：保留 [PlanValidationControl](../../src-tauri/crates/yss-graph-execution/src/plan/validation/control.rs)，继续标明尚未接入。Harness 拥有 turn/tool/workflow 的预算策略，Application 可以把取消和 deadline 转换后交给 Graph Execution；计划校验以及是否在校验步骤检查预算属于后者。当前不得据此声称计划校验超时已经生效，也不新增通用控制框架。

删除涉及的测试、示例、文档及精确架构权限随实际实现更新。日志插件、Harness 事件与插件 worker 的进程 stdout/stderr 不因同名一起删除。

## 8. 扩展机制

### 8.1 节点定义与执行能力

Node 通过 Registry 注册定义，Catalog 组织内置定义及其目录呈现；Graph.Execution 注册 kernel 实现，应用组装检查定义与实现的绑定关系。两者继续通过中立标识和能力描述协调，Node crate 不反向依赖 Graph 或 Execution。

目标行为：

- 在实际新增实现需求下完善 Execution 内部的注册入口，复用现有内置 kernels；不预先搭建动态加载框架。
- 编译支持检查读取本次会话实际使用的执行能力，不能在支持可配置注册后继续另查一张默认表。
- 执行能力的有效版本或指纹进入编译产物有效性契约。配置更新后通过新代次或会话切换生效，旧产物在执行入口重新核对。
- 冻结前检查重复标识、绑定及参数/输出契约；缺少实现的节点继续得到明确的编译阻断。
- SCI 的调用位置和中立数据边界保持现有约束，Runtime 组装不直接创建科学计算后端。

扩展验收使用一个复用既有端口类型和执行语义的普通数值节点。新增定义、实现和注册后，图解析、调度、项目管理与数据库实现不应增加该节点专属分支。引入新语言语义时允许修改相应 owner，不要求注册机制掩盖真实语义变化。

### 8.2 数据源、图表与插件

| 扩展                       | 预期入口                       | 验收重点                                   |
| -------------------------- | ------------------------------ | ------------------------------------------ |
| 新数据源                   | 数据源适配及注册配置           | 保持快照、列类型、查询预算、取消和错误契约 |
| 新图表类型                 | Chart 声明规则、投影和共享呈现 | 不依赖执行器内部状态；文件格式变化单独评估 |
| 新模型 provider 或存储实现 | 已有窄端口与 Runtime 组装      | 业务用例不出现实现选择分支                 |
| 独立安装的插件             | 现有 Plugin 协议和宿主能力接口 | 保留身份、授权、预算、产物提交及失效语义   |

插件扩展沿用 [Plugin 目标契约](../architecture/PLUGIN.md) 和 [当前 Plugin Runtime](../../src-tauri/crates/yss-plugin-runtime/README.md)。本计划不把协议文档中尚未实现的能力视为已具备，也不承诺任意插件已经能动态注册 Graph 节点。

### 10.2 界面人工验收

验收负责人：用户。状态：待用户执行，2026-09-15 已确认稍后人工验收。遵守仓库规则，不新增 UI 单元测试；本清单尚未勾选，不表示已完成真实界面验收。

涉及界面调用与投影的改动，人工检查：

1. 创建、保存、重开图表，切换数据库后绑定和预览正确。
2. 图表预览进行中切换项目，旧数据和旧错误不会覆盖新项目。
3. 新建连线，依次 Compile、Execute：待编译、编译中、已编译和有效结果状态可区分；草稿、产物和已提交文档各自更新。
4. 运行 `A → B → C` 和旁路 `A → D` 后断开或修改 A→B：B/C 与其下游边变旧，A/D 保持有效；从已有缓存的源 Pin 新连一条边，不会直接显示已执行。
5. 在不重跑/清理的情况下撤销上述编辑，缓存、Pin、边与 Node 状态恢复；重做再次失效。替换数据源内容或回收缓存后再撤销，不显示不存在的有效结果。
6. 只移动节点或修改显示标签，结果保持有效。局部 demand 不让未执行节点一律完成；修改后重新 Compile 不把过期缓存变成执行成功。
7. 修改后撤销能重新关联仍匹配的编译产物；若产物已被后续编译替换，则要求重新 Compile，即使部分缓存仍有效。
8. 运行中取消或切换项目，旧运行不向新会话发布结果；编辑/撤销后的迟到投影不覆盖当前状态，失败不会通过动画显示成成功。
9. 打开报告后改图、重跑，报告继续读取原结果并能翻页/分析；关闭一个窗口只释放相应租约，最后一个持有者离开后正确回收。
10. 删除 stdout/stderr 后，除零等真实运行错误仍在 Output 面板显示并能定位节点；清除错误摘要不清除 Results，终态与错误收尾顺序正确。
11. 回放按钮与录制状态已移除；当前编译/运行动画有实际事实来源，减少动态效果设置下仍能识别各状态。
12. 独立图表与图结果窗口共享呈现能力，数据身份和生命周期互不替代；Harness 与插件原有事件、错误及业务入口仍可使用。

只执行与当次改动相关的路径，记录操作、预期与实际结果。
