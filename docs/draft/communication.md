# 通信：Tauri IPC

[返回整体架构](architecture.md)

本文是通信架构的梳理草稿，按 Command、Event、Channel、DTO 与错误契约展开。前端入口位于 `src/services/`，Rust 传输边界位于 `yss-api`。

本文说明前后端完整通信链路；Rust 端的命令注册、DTO 映射、用例调用与消息交付组织在[后端通信适配子系统](backend.md#8-通信适配)中展开。两处描述同一条链路的不同范围。

## 1. Command：请求与响应

Command 用于表达一次明确请求，并返回处理结果，例如查询数据、保存文档、编译图或启动任务。

```text
前端 service → invokeCommand → yss-api 命令
  → Rust 业务用例 → 响应 DTO / CommandError → 前端
```

前端封装参数并解析响应；后端命令解析和校验传输输入、转换类型、调用业务用例并映射结果。命令不承担文件事务、科学计算或完整业务流程；耗时工作进入既有 blocking 边界。

下一步按“调用入口 → 命令注册 → 参数转换 → 业务调用 → 结果返回”继续梳理，不在这里维护完整命令清单。

## 2. Event：变化通知

Event 用于资源提交等低频变化通知。前端订阅通知后，通过已有发布流程更新投影，需要时查询后端快照。

通知不构成完整业务状态。资源修改的 Command 回执和 Event 可能对应同一次提交，前端需按提交身份与 publication revision 统一去重，避免重复应用。

下一步梳理事件的产生时机、订阅者、去重和订阅清理。不能假设所有事件都必然收到，再据此重建已提交状态。

## 3. Channel：有序消息流

Channel 用于进度、执行事件、诊断等持续消息。前端创建 Channel 并将其作为 Command 参数传入，后端通过该通道交付后续消息。

每种流都需要说明：消息属于哪个任务或会话、如何排序、容量如何约束、丢失或出现缺口时如何处理，以及怎样取消和结束。Channel 本身不替代这些业务约定。

下一步选择一条现有执行流或进度流，梳理“创建 → 绑定 → 接收 → 结束 → 清理”。具体恢复策略由相应业务流定义，不统一假设所有流都可重放。

## 4. DTO 与错误契约

DTO 是前后端约定的数据结构。Rust 负责将内部业务类型映射为传输类型，前端负责解析结构；业务调用方还需检查响应所属身份是否仍然有效。

Command 失败固定返回以下字段：

```json
{
  "code": "project_not_found",
  "details": null,
  "incidentId": null
}
```

`code` 表示稳定错误类别，`details` 提供安全结构化信息，`incidentId` 用于关联内部诊断。React 根据错误码提供本地化提示，后端不通过 Command 错误返回用户文案。

大表通过后端查询、分页和摘要限制传输规模；不能把所有数据一次传到前端再计算。下一步可按请求 DTO、响应 DTO、身份字段和错误映射继续展开。

通信契约的前端使用方见[前端草稿](frontend.md)，业务实现与数据管理见[后端草稿](backend.md)。
