# 前端：React

> Status: Planned
> Scope: 前端子系统划分、内部职责、JSON 页面布局模板及状态归属的梳理草稿
> Canonical owners: 当前架构与稳定契约见 `docs/architecture/`；实际实现以源码和测试为准
> Update when: 前端能力边界、布局模板约定或子系统协作方式调整时

[返回整体架构](architecture.md)

前端先按子系统划分，再在每个子系统内梳理职责。子系统回答“向用户提供什么能力、谁管理相关状态”，内部结构回答“界面、操作编排、投影、草稿和后端访问如何协作”。这一组织方式与[后端草稿](backend.md)一致，前后端分别按各自承担的能力确定边界。

本文定义梳理方向，并列出当前代表实现。页面布局统一采用 JSON 驱动模板是目标约定，不表示所有页面已经完成接入；子系统归属也不表示代码目录迁移已经完成。

## 归属原则

1. **按能力与状态确定归属**：项目资源、图编辑、数据编辑和图表文档分别拥有明确职责；共享界面和目录名称不能代替业务边界。
2. **区分子系统与技术层**：完整能力通常横跨 `modules/`、`features/application/`、`features/core/` 和 `services/`。这些目录说明实现所在的技术层，不各自代表一个完整业务子系统。
3. **状态只有一个管理方**：Rust 拥有已提交业务事实，React 持有后端投影、显式未保存草稿和 UI/运行态；其他消费者通过公开接口使用这些状态。
4. **编排与具体规则分开**：前端 Application 组织请求、生命周期和响应采用；Rust 负责业务校验、图语义、查询、计算和持久化。前端自身不依赖 UI/framework 的规则归前端 domain。
5. **页面布局由 JSON 模板驱动**：模板声明页面结构与组件组合，由页面宿主解析并渲染；工作台运行中的布局由根 Dockview 实例管理。
6. **共享展示保留业务归属**：Details、表格和报告组件可以服务多个子系统，各类数据和操作仍归对应 owner；职责偏差按实际实现单独记录。

## 1. 应用与工作台

负责将业务能力组合成完整桌面应用，并管理窗口、页面和面板的生命周期。应用入口组合各模块的公开能力，Workbench 提供布局与面板宿主。

### 内部结构

| 部分           | 职责                                                         |
| -------------- | ------------------------------------------------------------ |
| 应用组装与窗口 | 组合路由、窗口入口、菜单、状态栏与跨模块能力                 |
| 页面布局模板   | 读取 JSON 布局声明，校验组件引用，组织页面分区与默认布局     |
| 面板与组件注册 | 将模板中的标识映射到已注册组件、编辑器和面板贡献             |
| 布局运行时     | 执行面板打开、定位、激活、移动、分割和折叠                   |
| 生命周期协调   | 处理关闭、重置、项目切换、初始化恢复与布局持久化             |
| 跨业务展示宿主 | 根据当前上下文组合 Details、Inspect 等内容，调用相应业务能力 |

### JSON 驱动的页面布局模板

**页面布局使用 JSON 驱动模板的方式实现。** JSON 声明页面分区、组件或面板标识、组合关系和默认布局参数；React 页面宿主根据注册表解析模板，将业务组件放入指定区域。业务组件负责区域内的展示与交互，业务 Application 提供数据和操作入口。

```text
JSON 页面布局模板 + 已注册组件/面板
    → 页面宿主校验与组合
        → 页面分区与业务组件渲染
        → 工作台布局入口 → 根 Dockview 实例

后端业务投影 → 对应业务组件
用户操作 → 对应 Application 用例
```

模板负责结构和组合，不存放项目资源、图草稿、执行结果或业务流程。菜单、状态栏和弹窗等工作台外层区域由页面宿主组合；进入 Dockview 的面板通过既有布局能力安装。模板渲染器不直接操作业务 Store，画布、表格等组件的内部渲染与交互继续由对应组件实现。

需要区分三类 JSON 数据：

| 数据         | 用途                                                         | 管理边界                               |
| ------------ | ------------------------------------------------------------ | -------------------------------------- |
| 页面布局模板 | 声明页面结构、组件组合及布局默认值                           | 应用与工作台负责解析和应用             |
| 业务展示文档 | 提供分类、条目、文本和操作描述，例如 `ActivityPanelDocument` | 业务 owner 生成，模板消费其投影        |
| 运行布局快照 | 保存用户调整后的工作台布局，用于持久化和启动恢复             | 从根 Dockview 序列化，由布局控制器管理 |

模板是布局输入。用户移动面板、切换分组和调整尺寸后，以根 Dockview 的实时状态为准，不把模板变成另一份持续同步的布局 Store。目标方案在启动时继续优先恢复有效的用户布局快照，没有有效快照时采用模板建立默认布局；重置通过明确操作重新应用模板默认值。

工作台启动恢复时，只在空根实例上使用 `fromJSON`；运行期应用模板所需的布局变更应进入现有语义操作和布局事务。涉及关闭编辑器时，继续经过草稿保存、放弃或取消的关闭流程，不由模板直接卸载文档。

当前四个内置 Activity 面板已有 `ActivityPanelDocumentView`，接收 Rust 生成的文档、展开状态和有限操作回调。该实现可作为文档与模板职责分离的参考。整体页面 JSON 布局模板尚未实现，当前默认工作台布局仍由 TypeScript 命令建立；现有 Dockview JSON 快照属于布局持久化。后续应复用组件注册和布局入口落实页面模板，具体结构与接入范围另行细化。

### 状态与边界

根 Dockview 实例拥有工作台拓扑、面板位置与顺序、活动分组、尺寸和折叠状态。页面模板、Zustand 和业务面板不另建这些状态的镜像。

Details 是跨业务展示宿主，节点、图表、数据和日志详情仍使用各自的数据和操作入口。布局管理不拥有图草稿、数据库内容或结果生命周期。当前契约见 [Workbench Dockview](../architecture/WORKBENCH_DOCKVIEW_ARCHITECTURE.md)。

## 2. 项目与资源交互

负责将后端项目和资源状态呈现给用户，组织打开项目、创建资源、重命名、移动和删除等交互。

### 内部结构

| 部分         | 职责                                                     |
| ------------ | -------------------------------------------------------- |
| 项目生命周期 | 组织打开、加载、切换与关闭，协调旧投影清理和新投影安装   |
| 资源展示     | 展示项目分类、资源身份与状态，管理本地展开和选择         |
| 资源操作     | 收集用户输入并调用对应创建、修改、移动或删除用例         |
| 发布结果采用 | 协调命令回执、资源变化通知及刷新，检查项目身份与发布版本 |

### 状态与边界

React 保存后端资源索引和 Activity 文档的显示投影，Rust 拥有已提交项目、资源身份与版本。资源路径作为不透明标识使用，前端不从路径字符串重新推导领域事实。

项目切换协调图、数据、图表和工作台各自的生命周期；资源树不直接清空其他子系统的内部状态。异步响应采用前检查所属项目，避免旧项目结果覆盖新项目。当前生命周期见[系统架构](../architecture/ARCHITECTURE.md)。

## 3. 图编辑与运行交互

负责从打开图文档、编辑未保存草稿，到请求编译、保存、执行和查看结果的用户流程。前端组织交互，Rust 执行编辑校验、语义分析、编译与计算。

### 内部结构

| 部分             | 职责                                                          | 当前代表位置                                                                           |
| ---------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 文档草稿与历史   | 未保存文档、保存基线、dirty、撤销与重做                       | `src/features/core/graphDraft/`                                                        |
| 编辑操作编排     | 组织草稿操作顺序，检查响应所属的项目、草稿与请求              | `src/features/application/graphDraft/`、`src/features/application/graphEditing/`       |
| 语义投影采用     | 安装 Rust 返回的节点、端口、类型与诊断，供多个界面消费        | `src/features/application/graphProjection/`、`src/features/core/dataStore/` 中的图投影 |
| 画布与节点交互   | 选择、视口、测量、拖动预览、连线手势和节点目录                | `src/modules/graph-editor/`、`src/modules/node-catalog/`                               |
| 编译、保存与执行 | 分别组织三个独立操作，管理请求状态及编译产物引用              | `src/features/application/graphDraft/`、`src/features/application/execution/`          |
| 运行与结果查看   | 展示运行状态、查询结果与报告，分别呈现 Problems 和 Run Output | `src/modules/results/`、`src/modules/problems/`、`src/modules/output/`                 |
| 编辑器生命周期   | 协调打开、关闭、重新打开及项目切换时的失效和清理              | `src/features/application/editor/`、`src/features/core/graphSession/`                  |

### 状态与边界

草稿、语义投影和画布临时状态分别管理。拖动预览和测量不创建另一套文档；Canvas、Details 与 Problems 消费同一图语义投影，解析后的类型、Schema 和诊断以 Rust `GraphSemanticSnapshot` 为准。

Draft、Compile、Save、Execute 是独立操作。Compile 不提交文档，Save 不隐式编译，Execute 使用匹配的编译产物。保存失败保留未保存草稿，成功后采用后端返回的状态并更新保存基线。

Results 的身份与生命周期由 Rust 管理，不能由某个图编辑器的挂载状态决定。Graph Problems、Results 和 Run Output 分别展示语义诊断、执行产物和程序文本输出；运行失败摘要也不能伪装成 stdout/stderr。Run Output 当前已有通道与 UI，生产输出 producer 尚未接入。完整契约见 [Graph 与 Execution](../architecture/GRAPH_AND_EXECUTION.md)。

## 4. 数据浏览与编辑

负责数据的查看与操作入口，包括数据源浏览、表格分页、编辑请求以及导入导出。

### 内部结构

| 部分         | 职责                                           |
| ------------ | ---------------------------------------------- |
| 数据浏览     | 展示数据资源、Schema、摘要与加载状态           |
| 表格交互     | 管理页面、列显示、选择和筛选输入，按需请求数据 |
| 编辑与交换   | 组织数据修改、导入导出请求及失败反馈           |
| 查询生命周期 | 检查请求、数据库和项目上下文，释放面板局部状态 |

### 状态与边界

Rust 负责查询、筛选、聚合、数据编辑和持久化，前端获取当前需要的页面或摘要。当前工作台数据标签是只读查看入口，没有本地文档草稿；不能把图编辑器的 dirty、Save 和历史模型直接套到数据标签。

数据库投影可以被工作台标签与独立窗口复用。关闭一个面板只释放对应查看状态，不能因此清除其他消费者仍在使用的共享投影。数据运行时契约见 [Database runtime](../../src-tauri/crates/yss-database-runtime/README.md)。

## 5. 图表编辑与展示

负责可编辑图表资源的文档、配置、数据绑定和渲染。图表拥有文档编辑职责，与执行结果的报告或绘图展示分别组织。

### 内部结构

| 部分         | 职责                                       |
| ------------ | ------------------------------------------ |
| 图表文档     | 加载文档，管理未提交修改与 dirty 状态      |
| 配置与绑定   | 编辑图表配置、选择数据来源并组织相关查询   |
| 图表渲染     | 将配置和数据投影转换为可视化，处理局部交互 |
| 资源生命周期 | 协调打开、修改提交、重命名和关闭           |

### 状态与边界

已提交图表文档由 Rust 项目与资源能力管理；前端的编辑内容和显示状态分别维护。数据查询与统计事实来自对应后端能力，图表渲染不重新计算领域结果。

`src/features/core/chart/` 中的文档状态、`src/features/application/chart/` 中的交互用例，以及编辑器生命周期中的图表协调共同完成这一能力。可复用的绘图组件本身不拥有图表资源或执行结果。

## 6. Assistant

负责对话展示、用户输入、审批交互及工具操作反馈，消费 Rust Harness 的快照与有序事件。

### 内部结构

| 部分           | 职责                                         |
| -------------- | -------------------------------------------- |
| 会话展示与输入 | 呈现消息、输入内容、提交和取消入口           |
| 状态投影       | 采用会话快照和事件，呈现工具、审批及运行状态 |
| 业务操作衔接   | 将图草稿等交互接入已有业务操作流程           |

### 状态与边界

Rust Harness 拥有 session、turn、工具流程、审批与事件顺序，React 保存其界面投影和本地输入。Assistant 对图草稿的操作进入既有草稿协调流程，不创建独立的 AI 草稿或项目模型。当前实现与缺口见 [Statistical Harness](../architecture/STATISTICAL_HARNESS.md)。

## 7. 插件交互与接入

负责宿主插件的管理界面和前端能力接入。

### 内部结构

| 部分         | 职责                                             |
| ------------ | ------------------------------------------------ |
| 管理入口     | 提供安装、启用、禁用、打开和卸载操作             |
| 状态展示     | 消费插件及任务状态，展示进度、结果入口与失败反馈 |
| 界面贡献接入 | 将插件声明的界面贡献交给应用组装和工作台能力     |

### 状态与边界

## 8. 运行诊断与反馈

负责技术运行信息的查看，以及用户操作结果的本地化反馈。

### 内部结构

| 部分       | 职责                                               |
| ---------- | -------------------------------------------------- |
| Logs 查看  | 展示有界日志投影，管理筛选、选择、自动滚动与定位   |
| 诊断订阅   | 协调订阅、暂停、恢复和释放                         |
| 错误与反馈 | 将稳定错误码转为本地化提示，由对应操作决定呈现时机 |

### 状态与边界

运行日志是观察信息，不用于重建业务状态。Graph Problems、Results、Run Output、Assistant 对话和 Logs 保留各自的数据流；不能因为显示在同一工作台就统一为一个消息 Store。错误、日志和反馈契约见 [Runtime Signals](../architecture/RUNTIME_SIGNALS.md)。

## 9. 通信适配

负责前端到 Rust 的请求、响应、通知和数据流适配。业务 service 按接口能力组织，普通 Command 经过统一 `invokeCommand` 入口。

### 内部结构

| 部分         | 职责                                  |
| ------------ | ------------------------------------- |
| 请求适配     | 组织接口参数，调用对应 Command        |
| 响应解析     | 校验 DTO 和错误结构，返回明确结果     |
| 通知与数据流 | 封装 Event/Channel 接入及取消订阅能力 |

```text
界面操作 → 对应 Application 用例 → service → Tauri IPC
后端响应 → service 解析 → Application 检查身份并采用 → 状态发布与界面更新
```

### 状态与边界

Service 负责传输与解析，Application 决定响应是否仍适用于当前项目、草稿或请求，并协调采用。订阅的业务生命周期由对应 owner 决定，适配层提供创建与释放机制。

Command 失败使用 Rust 定义的 `{ code, details, incidentId }`，用户提示由前端本地化。完整通信链路在[通信草稿](communication.md)展开，当前接口契约见 [`yss-api`](../../src-tauri/crates/yss-api/README.md)。

## 10. 客户端设置与通用支撑

负责明确可复用的客户端技术能力，供各业务子系统使用。

### 内部结构

| 部分         | 职责                                                   |
| ------------ | ------------------------------------------------------ |
| 客户端设置   | 管理 AI、外观等本地偏好及跨窗口传播                    |
| 主题与国际化 | 提供一致配色、文本和格式化能力                         |
| 通用展示组件 | 提供按钮、表单、弹窗等基础组件和可复用展示能力         |
| 平台能力适配 | 对接窗口、剪贴板等桌面能力，平台调用仍通过对应适配入口 |

### 状态与边界

客户端偏好按用途持久化，不参与后端统计计算，也不代替项目配置或插件状态。通用组件通过输入和回调服务业务，不能吸收调用方的业务规则。JSON 页面布局模板使用这些组件，模板的选择与应用由应用和工作台负责。

## 11. 技术层与现有目录映射

子系统定义职责归属，技术层定义依赖方向。各子系统按实际需要使用以下技术层，不要求每个子系统都建立相同数量的目录。

| 技术层     | 现有位置                            | 职责                                                |
| ---------- | ----------------------------------- | --------------------------------------------------- |
| 应用组装   | `src/app/`                          | 窗口、路由及跨模块贡献的组合                        |
| 业务界面   | `src/modules/`                      | 面板、窗口和编辑器，通过模块根 `public.ts` 提供入口 |
| 用户用例   | `src/features/application/`         | 操作编排、生命周期和响应采用                        |
| 状态与投影 | `src/features/core/`                | 后端投影、显式草稿和共享运行态                      |
| 前端规则   | `src/features/domain/`              | 不依赖 UI、Tauri、service 或具体基础设施的规则      |
| 通信适配   | `src/services/`                     | 后端调用与订阅                                      |
| 通用展示   | `src/components/ui/` 等共享展示位置 | 基础组件与展示复用                                  |

当前前端依赖方向为：

```text
app 组装 → modules/*/public → features/application
                              → features/core 与 features/domain
                              → services
界面 → 通用展示组件
```

Application 调用 service 完成后端访问，domain 不反向依赖 React、Tauri 或 service。具体依赖约束见[系统架构](../architecture/ARCHITECTURE.md)和[架构门禁](../development/ARCHITECTURE_GATES.md)。

## 12. 状态归属与后续核对

| 状态类别             | 管理方                              | 采用与清理原则                                    |
| -------------------- | ----------------------------------- | ------------------------------------------------- |
| 已提交业务事实的投影 | 对应前端子系统持有，Rust 为事实来源 | 检查身份和版本后单向采用，项目切换时按 owner 清理 |
| 未保存编辑内容       | 对应图或图表文档 owner              | 与保存基线分开，提交失败保留用户修改              |
| 布局与面板拓扑       | 根 Dockview 实例                    | 从实时布局读取，持久化快照按既有恢复契约使用      |
| 局部交互与运行态     | 对应组件、面板或 Application 用例   | 按组件、文档、窗口或项目作用域管理                |
| 客户端偏好           | 对应设置 owner                      | 按用途本地持久化，与项目业务状态分开              |

后续按子系统核对公开入口、状态创建与清理、跨模块调用和实际实现位置。重点包括：

- 明确 JSON 页面布局模板的最小结构与首批接入页面，复用已有组件注册和工作台布局能力。
- 将 `src/modules/details/` 作为跨业务展示宿主梳理，分别标明各种详情的数据来源与操作 owner。
- 按具体状态说明 `src/features/core/dataStore/` 中的图、数据库等投影归属，不将整个目录视为单一业务子系统。
- 沿打开、编辑、保存和执行用例核对跨层协作，将确认的职责偏差记录到具体实现，避免仅通过分类名称声称边界已经完成。
