  这些扩展不能仅靠修改几个布尔开关。当前实现存在几处明确边界：

  - 布局校验 (src/modules/workbench/internal/layout/layoutSerialization.ts:8)拒绝非空 subLayouts，树结构也不
    接受 tabgroup。

  - 面板查询 (src/modules/workbench/internal/layout/workbenchLayoutOperations.ts:94)假定标签直接位于 tabset
    或 border 下，分组后需要调整。

  - 固定标签需要让自定义关闭命令遵守 pin
    规则；布局撤销需要避免恢复已经释放的结果、过期项目面板。官方布局撤销实现
    (https://github.com/caplin/FlexLayout/blob/master/src/view/useUndo.ts)

  - 现有独立窗口拥有 Tauri 创建、几何保存和结果租约交接流程。浏览器 popout 使用另一套窗口机制，不能直接替
    换。现有窗口入口 (src/features/application/window/openPresentationWindow.ts:37)

  应继续留在原有模块的职责包括：Graph 文档和撤销历史、节点坐标与连线、数据查询和表格选择、结果数据与租约、
  Assistant 会话、保存确认，以及模态弹窗的焦点约束。报告内部的章节布局也已有 Rust JSON 页面负责，FlexLayout
  适合管理整个报告面板的位置。底栏对齐所需的项目 CSS 同样不会因为增加库功能而自动消失。

  我建议的实施顺序是：

  1. 先完善现有接入：原生控件国际化、布局快捷键、通用菜单和面板尺寸约束。
  2. 优先改善日常操作：节点文档/设置面板化、覆盖式边栏、资源原生拖入、固定标签。
  3. 再扩展复杂工作空间：结果对比预设、日志分屏、浮动面板、彩色标签组、布局撤销；Tauri 多窗口集成最后单独评
     估。
