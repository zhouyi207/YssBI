# YssBI 组件化架构重构计划

> Status: Planned
> Scope: Rust 业务组件边界、GPUI 消费者、结果缓存与租约、阶段摘要和剩余人工验收
> Canonical owners: 本文拥有计划与验收；当前实现由各模块 README、源码和 Cargo manifests 拥有
> Update when: 组件边界、阶段范围或验收状态改变时

## 1. 目标与范围

形成职责明确的模块单体：GPUI 宿主消费 Application 类型化用例，领域拥有业务事实与规则。
Node 与 Chart 是明确的业务能力；Execution 在业务上归入图执行子系统，但保持自己的 crate 边界。
完整应用会话独立于 Graph。复用结果缓存和报告租约，图状态从解析、真实运行及缓存适用性派生。
不引入通用组件容器、字符串服务注册中心、统一 JSON 调用总线或另一份图文档。

实施优先在现有 owner 内复用、收口与清理；不以 crate 数量或文件大小定义架构质量。
`react/` 是参考源码，不参与原生构建，不承担当前业务或布局所有权。

### 1.1 保留与清理边界

| 对象 | 结论 |
| --- | --- |
| ResultStore、当前输出缓存、报告租约 | 保留同一不可变结果及完整结果身份，不创建运行历史仓库 |
| 执行录制、回放与无事实来源的动画队列 | 已在原重构中清理；原生状态只能反映实际诊断、运行和结果 |
| 重复 Scalar/Text/Empty 结果分支 | 正常生产路径使用 RuntimeValue；保持空值、精度与输出类别 |
| 无生产者的 Graph stdout/stderr 专用链路 | 原清理不影响运行失败摘要、Harness 事件或插件进程输出 |
| PlanValidationControl | 显式保留的计划校验控制对象；不能仅因存在该类型便宣称 deadline 已接入 |

函数执行包、递归限制和终态清理须沿当前生产调用核实，不凭历史候选删除仍在使用的能力。

### 1.2 审计与清理要求

每个阶段核对重复逻辑、无效路径、契约漂移、多事实源、语义冲突、无调用函数和兼容残留。
保留有独立目的的边界校验、提交前重验、不可变读取和局部输入缓冲；避免重复 Resolve、整图复制、
全量 I/O 和大锁。同步迁移所有消费者、导出、注册、测试及 owner README，不通过补同步保留双权威。
有性能结论时提供同场景测量；正确性回归和代码减少不是提速证据。

## 3. 职责与状态所有权

| Owner | 事实与规则 | 不承担的职责 |
| --- | --- | --- |
| Project | 当前 GraphDocument、可逆历史、保存身份、资源版本、文件事务 | 数据查询、图解析与执行算法 |
| Database | 不可变数据代、查询、变更、历史/checkpoint | Project 资源身份与提交授权 |
| Node Protocol / Registry / Catalog | 端口参数声明、注册校验、节点目录与帮助 | 图实例、连接后类型、项目会话 |
| Graph Analysis / Runtime / Editor | 语义快照、解析缓存、编辑规划和投影 | 第二份可写图、完整应用会话 |
| Graph Execution / ResultStore | 计划准备与缓存、demand、运行、结果适用性与租约 | UI 状态、Project 持久化权威 |
| Node Kernel | 冻结内核注册表、中立调用值与内置适配 | 图地址、资源授权和图错误定位 |
| Chart | 图表声明及预览用例；GPUI 保留未提交配置和绘制 | 统计估计与图执行结果存储 |
| Harness / Plugins | 各自会话、授权、任务、回执与恢复 | 直接绕过 Application 修改项目 |
| Application | 会话组合、事实捕获/重验、跨组件提交与恢复 | 领域算法、GPUI 控件或平行领域模型 |
| GPUI host | 输入、焦点、手势、worker 调度、类型化投影与本地化 | 已提交领域事实；根 DockArea 之外的第二布局模型 |

GraphSemanticSnapshot 唯一拥有解析后的端口、类型、Schema、血缘与诊断。Project 同时拥有未保存的
当前图和历史；GUI 只保留未提交控件输入。Graph Problems、Logs、运行状态/失败和 Results 各自独立。

## 4. 接口与依赖

公开能力使用类型化输入、回执和稳定错误，内部缓存与锁保持私有。需要替换实现或隔离资源访问时
复用窄端口；固定领域能力可以直接调用。用例捕获 ApplicationSession，领域只接收必要事实与能力。
Kernel 调用 SCI Runtime，后者调用 SCI，再由 Linalg 拥有矩阵实现；宿主与 Application 不组装科学后端。
扩展节点时，声明、参数/输出契约、内核实现 revision 和冻结能力指纹必须一致。

## 5. 组装与生命周期

`ApplicationServices::initialize` 组装平台中立服务；GPUI 宿主持有服务与异步执行器。
项目登记、Harness Host 与 Plugin Manager 按进程生命周期管理；Project/Database/Graph/Execution
在完整 ApplicationSession 中绑定身份。阻塞业务由 worker 执行，回执经捕获生命周期接纳。

项目切换依次验证目标、关闭旧准入、排空或恢复、构造候选、核对绑定并整体发布。
过期用例不能关闭后继会话；drain 后失败须沿原恢复协议处理，不能只重新打开准入。
图关闭、面板隐藏、结果窗口关闭和项目替换不同：移动或隐藏面板不释放仍由消费者持有的租约。

## 6. 跨组件用例

### 6.1 编辑、保存与执行

Application 捕获项目、数据库、函数及当前图版本；Editor 准备候选，Analysis 解析，Project 原子提交。
编辑立即更新诊断与结果适用性；Save 只持久化当前图；Execute 捕获文档及语义身份，在内部准备计划、
校验资源授权、运行并发布结果，不隐式保存。Harness 编辑批次按自己的原子保存约定复用相同 owner。

### 6.2 Chart、Database 与 Project

独立图表先捕获资源及数据库版本，再有界查询、生成投影并重验；GPU 绘制与未提交编码留在宿主。
独立图表和执行结果共用原生绘制，不共用持久化或结果身份。数据库保留准备、物理提交、Project
确认、补偿和恢复边界；通知失败不等同于未写入，不能盲目重试已提交或结果未知的操作。

### 6.4 结果缓存、依赖失效与撤销

- ResultStore 是唯一结果 owner；`{ executionSessionId, resultId }` 标识不可变结果。
  当前输出缓存和报告租约可持有同一值；最后持有者释放后回收，正在查询的临时共享引用自然结束。
- 每个稳定输出地址保留最近成功缓存，不按运行次数积累版本。**是否仍被持有**与**是否适用于当前图**分开。
  过期值不作为当前 Pin 结果或执行输入，显式历史报告仍可经完整引用读取。
- 有效性取决于实际输入绑定、上游结果版本、资源版本、函数依赖与内核版本，不只看全图 hash、Pin ID 或曾运行。
  改线从目标及下游传播失效；上游、旁路和纯位置/标题变更不受无关影响。新边不能因源 Pin 有缓存显示已执行。
- 撤销重新解析并重验依据；仅恢复仍存活且全部依据匹配的缓存。重跑、清理或回收的值不能从历史栈复活。
  重做按同一规则失效；undo/redo 不保存颜色、结果载荷，也不隐式保存或执行。
- 重算开始解除本次 demand 的旧当前绑定，失败或取消不冒充新成功；未重算输出与报告租约保持各自规则。
  恢复相同语义不能重新授予过期 run 的发布资格。
- 当前缓存可用与调度器计算复用不是同一能力，不能由颜色恢复推断增量执行已完成。

### 6.5 诊断、运行与缓存呈现

未运行、结果可用、部分结果、过期、正在运行、阻断诊断及真实失败必须可区分；不只依靠颜色。
诊断与运行状态优先呈现，缓存标记可以独立保留。运行效果只覆盖真实事件能证明的范围，
没有逐节点进度时不编造播放顺序；原生绘制复用现有组件、主题与动画，减少动态效果仍须可识别状态。

## 8. 扩展机制

普通数值节点应通过 NodeComponents、定义与 kernel 注册加入，不在 Project/调度器增加专属分支。
能力变更经 revision/指纹与会话配置生效；旧产物在准入重验。新数据源保留快照、预算、取消和错误，
新图表复用声明/查询/绘制入口，provider 与存储使用原窄端口。插件沿当前协议接入，不能将目标文档中的
未实现能力当成已能动态注册 Graph 节点。独立图表绑定图结果等新增数据源仍属产品扩展，非目录整理。

## 10. 验证与验收

### 10.1 验证范围

执行命令由[根 README](../../README.md)与 owner README 维护，遵循[根规则](../../.rules)。
从仓库根以 `cargo run` 进行人工验收；业务变化选择明确 package/target 的 Cargo 测试，
同时覆盖 Application 与原生调用方。零匹配、仅编译、启动或环境失败不算行为通过。
本次仅整理文档，未执行检查；不新增 UI 单元测试。

### 10.2 界面人工验收

验收负责人为用户。2026-09-15 第 4、9 项收到反馈并有当时修复记录，真实复验仍未在本计划核销。
原生逐项证据另见 [GPUI 组件审查](GPUI_COMPONENT_AUDIT.md)，以下十二项保持开放：

1. 创建、保存、重开图表，切换数据库后绑定和预览正确。
2. 图表预览进行中切换项目，旧数据和旧错误不会覆盖新项目。
3. 新建连线直接运行，无额外准备操作；编辑显示类型、Schema、能力问题；运行不隐式保存。
4. 运行 `A → B → C` 与 `A → D` 后断开/修改 A→B：B/C 及下游变旧，A/D 保持有效；新绑定不直接显示已执行。
5. 未重跑/清理时撤销恢复缓存、Pin、边与节点；重做再次失效。换数据或回收后撤销不伪造结果。
6. 纯移动/显示名修改保持结果；局部 demand 不让未执行节点显示完成，过期缓存不变成执行成功。
7. 撤销后重新校验，下一次运行内部准备匹配计划；迟到请求不覆盖较新的编辑依据。
8. 取消或切换项目后旧运行不向新会话发布；编辑/撤销后迟到投影不覆盖当前状态，失败不显示成功动画。
9. 已打开的数据结果/报告在改图、重跑后仍读原结果；数据表/数列和报告内观测表可翻页，概览、图形和分析不要求整体分页。
   每个窗口只释放自己的租约，当前输出与最后消费者都释放后回收。原生分页大小以宿主实现为准。
10. 除零等真实错误仍在 Output 定位节点，清空错误不清除 Results，终态与失败收尾顺序正确。
11. 无独立准备或执行回放入口；运行动画有事实来源，减少动态效果时仍能识别状态。
12. 独立图表与结果共用呈现但身份不同；Harness 和插件的业务入口、事件、错误仍可使用。

第 4 项的历史反馈是断开一个查看节点时旁路 Pin 也变化；必须覆盖无输出观察节点的实际消费绑定。
第 9 项已澄清仅数据分页，不要求整份报告分页；不足一页不应显示可用下一页。不能删除这些回归场景。

### 10.3 审计清理验收

七类问题有真实调用依据；修复归唯一 owner；删除无效定义及注册；成功、失败、取消和生命周期
覆盖实际消费者。未决项影响正确性或人工验收时不得标完成，历史自动通过不能代替当前原生证据。

### 10.4 文档同步与完成标准

同步 Application、Graph、Project、Database、Node、GPUI 及 Logging 的当前 README；系统关系由
[架构总览](../architecture/ARCHITECTURE.md)维护。完成要求是职责唯一、接口清晰、旧路径清理、
局部失效与撤销正确、结果持有/释放可证明，以及上述开放验收被真实记录逐项关闭。
